# KAI — الهوية والبنية المعمارية المرجعية

**الإصدار:** v1.0  
**التاريخ:** 2026-09-27  
**المسار:** `docs/architecture/KAI_REFERENCE_ARCHITECTURE_AR.md`  
**الحالة:** Canonical Architectural Reference — المرجع الأعلى لهوية KAI وحدود سلطات مكوّناتها

## 0. حالة هذه الوثيقة

هذه الوثيقة **Canonical Architectural Reference** و**Identity / Architecture Reference** لـ KAI.

- **ليست design proposal.** هي المرجع المعتمد لهوية KAI، ومضمونها مُعتمد كمرجع معماري للمشروع.
- **لا تستبدل الـroadmap التنفيذية.** لا تُعيد تعريف المشروع ولا تحدد جدول عمل أو أولويات تنفيذ.
- **لا تلغي specifications التنفيذية المتخصصة.** وثائق مثل [مواصفة KAI-IR](../kai-ir-spec-v0.md) تبقى سارية و normative في مجالها.
- **عند التعارض** حول **هوية KAI** أو **حدود سلطات أي مكوّن من مكوّناتها**، تكون هذه الوثيقة هي **المرجع الأعلى**، وتسود على أي قراءة أخرى.
- **الترتيب المرجعي:**

  ```text
  Canonical Architecture   (هذه الوثيقة)
      ↓
  Official Roadmap
      ↓
  Implementation Specifications   (مثل KAI-IR Specification)
      ↓
  Experiments / Engineering & Readiness Reports
  ```

  كل مستوى يفسّر المستوى الذي فوقه ولا يناقضه.

- **قاعدة التصعيد:** أي تعديل مقترح على هوية KAI أو على حدود سلطة أي مكوّن يُراجَع أولًا على هذه الوثيقة، وإن لم يتعارض معها بقي اختصاص المستوى الأدنى.

سجل حالة الوثائق وفهرس المراجع في: `docs/architecture/DOCUMENTATION_STATUS.md`

## 1. الغرض

هذه الوثيقة هي المرجع المعماري لهوية KAI وحدوده. هدفها منع الخلط بين ما هو Core، وما هو Extension، وما هو Future، وما يزال قرارًا معماريًا غير محسوم.

KAI ليس مشروع Workflow Language؛ هويته الأساسية هي Governed Agent Runtime لتنفيذ نية المستخدم بصورة موثوقة، قابلة للتدقيق والاستئناف، مع فصل واضح بين اقتراح النموذج وسلطة النظام.

## 2. ما هو KAI؟

> KAI ينفذ نية المستخدم من خلال نظام يستطيع فيه النموذج اقتراح الفهم والخطة، بينما تتولى سلطات حتمية وبشرية تحديد ما هو مسموح، وما يمكن تنفيذه، وما تم التحقق منه، وما إذا كانت المهمة قد اكتملت.

النموذج يقترح:
- Understanding؛
- Plan؛
- تفاصيل تنفيذ مقيدة.

لكنه لا يملك سلطة:
- منح الصلاحيات؛
- تجاوز Policy؛
- تجاوز Approval؛
- فرض Identity؛
- الاتصال المباشر بالـProvider؛
- تغيير Task Lifecycle؛
- إعلان Completion.

## 3. ما ليس KAI؟

KAI ليس:
- LLM مع Tool Calling مباشر؛
- Chatbot بوصفه هوية النظام؛
- Autonomous system يحدد فيه النموذج صلاحياته؛
- General Workflow Engine؛
- User-authored Workflow DSL؛
- Graph Interpreter مفتوحًا؛
- Scheduler أو Parallel Execution Engine؛
- نظامًا تتحكم فيه Memory في التنفيذ؛
- IR تملك صلاحيات تنفيذ مستقلة.

الواجهات المستقبلية مثل Computer Use أو Desktop Agent أو Telegram يمكن أن تقع فوق KAI، لكنها لا تعيد تعريف الـCore.

## 4. المبادئ غير القابلة للتفاوض

### 4.1 النموذج يقترح، والسلطة تقرر

كل Model Output يبقى Proposal/Data حتى تقبله بوابات حتمية.

### 4.2 Tool Gateway هو حد تنفيذ أفعال الـAgent

**حدّ تنفيذ أفعال الـAgent.** كل فعل ينفّذه الـAgent يمر عبر Tool Gateway، ولا يسمح لـPlanner أو KAI-IR أو Memory أو Runtime helper بالالتفاف عليه. في production، `AgentRuntime._execute` هو الاستدعاء الوحيد لـ`ToolGateway.execute`، وهو الحدّ الذي تمرّ عنده أفعال الوكلاء عبر Policy وApproval وIdentity Resolver وContent Authorizer وReserved-argument guard وContractVerificationEngine.

**ووصف الحالة الفعلية لا يعمّم هذا الحد على النظام كله.** إلى جانب مسار الـAgent توجد مسارات API مباشرة تستدعي خدمات الـverticals مباشرةً، على نفس الشيفرة المشتركة التي تستخدمها الـadapters:

```text
api/calendar.py
api/gmail.py
api/contacts.py
    ↓
vertical services (calendar / gmail / contacts)
```

هذه المسارات لا تمرّ عبر Tool Gateway، ولذلك لا تمرّ عبر Policy أو Approval أو Identity Resolver أو Content Authorizer أو Reserved-argument guard أو ContractVerificationEngine؛ فهي تستدعي الـservice مباشرةً ثم تقرأ نتيجة `create_and_verify`/`send_and_verify` كما هي.

**ومساران منفصلان، لا مسار واحد موحّد.** لم يُتخذ في هذه الجولة أي قرار معماري يوحّدهما أو يدمجهما، ولم تُجرَ أي مراجعة أمنية مستقلة عنهما. ما ورد هنا وصف معماري للحالة الراهنة كما أثبتته قراءة الشيفرة، لا حكم على ملاءمتها الأمنية. وخيار توحيد المسارين قرارٌ يتبع هذه المراجعة ولا يسبقها.

### 4.3 Policy خارج سلطة النموذج

النموذج يقترح Action؛ Policy تحدد هل هو مسموح.

### 4.4 Approval سلطة بشرية

عندما تكون الموافقة مطلوبة، فهي صريحة، مرتبطة بالـIntent، وأحادية الاستخدام.

### 4.5 Identity يمكنها رفض التنفيذ

لا يجوز تخمين الهوية أو استبدالها بصمت.

### 4.6 Verification تسبق Completion

نجاح Provider Call لا يعني أن Intent تحقق. يجب أن توجد Evidence كافية لإثبات النتيجة.

### 4.7 Durable Evidence هي سجل الحقيقة التنفيذية

تستخدم في Audit وVerification وRecovery وReplay وإثبات Completion.

### 4.8 Task State Machine هي سلطة Lifecycle

لا يجوز لأي Node أو Provider أو Model إعلان حالة المهمة من تلقاء نفسه.

### 4.9 Contract يتم تثبيته قبل قبول Planning

يحدد على الأقل Intent/Goal وSuccess Criteria وAllowed Capabilities وRisk Policy والقيود التنفيذية.

### 4.10 Recovery هي Re-derivation وليست Memory

يجب أن يستطيع النظام إعادة بناء ما يجب فعله من Durable State دون الاعتماد على تذكر النموذج.

## 5. البنية المرجعية

```text
User Intent
    ↓
Sealed Task Contract
    ↓
Understanding
    ↓
Identity / Context Resolution
    ↓
Planner
    ↓
Deterministic Plan Acceptance
    ↓
KAI-IR (عند استخدامه)
    ↓
Durable Runtime
    ↓
Governed Tool Gateway
    ├── Policy
    ├── Approval
    ├── Identity / Account Authority
    └── Verification
    ↓
Durable Evidence
    ↓
Fulfillment Decision
    ↓
Task State
```

هذا رسم للسلطة المعمارية وليس بالضرورة Call Sequence حرفيًا في كل حالة.

## 7. KAI-IR

KAI-IR طبقة Representation داخلية، وليس هوية KAI ولا مصدر صلاحيات.

يمكنه:
- تمثيل الخطة المقبولة؛
- تمثيل Conditions وControl Flow المحدود؛
- إنتاج Canonical Form؛
- إنتاج Program Identity/Fingerprint؛
- تحديد الـStep المؤهل التالي.

ولا يمكنه:
- تنفيذ Tool؛
- منح Permission؛
- الاتصال بالـProvider؛
- امتلاك Credentials؛
- تغيير Lifecycle؛
- استبدال Policy أو Approval أو Tool Gateway؛
- إعلان Intent Fulfilled.

القاعدة:

> KAI-IR يحدد «ما الخطوة المؤهلة التالية؟» لكنه لا يحدد «هل التنفيذ مسموح؟» ولا «هل الأثر الخارجي حدث؟» ولا «هل المهمة اكتملت؟».

## 8. Branching

Branching Extension وليس أصل KAI.

معناه المرجعي:

> **مسار تنفيذ بديل لنفس Intent ونفس Contract.**

ولا ينبغي أن يعني تلقائيًا Intent جديدًا أو Permission Scope جديدًا أو Goal جديدًا.

```text
Same Intent
    ↓
Same Contract
    ↓
       Plan
      /    \
  Path A  Path B
      \    /
       ↓
Same Fulfillment Question
       ↓
Evidence
       ↓
Task Completion
```

التصميم الحالي يبقى مقيدًا: Branch ثنائي، تقدم للأمام، بلا Loops أو Parallel Execution أو Arbitrary Graphs، والاختيار Fail-closed.

### 8.1 نتيجة القياس: هل يمثّل KAI مسارين بديلين لنفس Intent؟

قِيست الفرضية ببرنامج من ست خطوات وfork واحد بعد فحص التوفر، كل ذراع فيه تنشئ الحدث وتقرأه مرة أخرى للتحقق، ومهمتان تبدّلان `then`/`else` فتسنّان ذراعين متقابلتين من الـfork نفسه. نفس الـGoal ونفس الـSuccess Criteria ونفس القدرات، والفرق في المسار فقط. كل الـassertions تمرّ من Pipeline حقيقي: Tool Gateway وPolicy وIdentity وحدود Approval وقاعدة البيانات، والاستبدال الوحيد هو الشبكة والنموذج، وهي نفس الطبقة التي يستبدلها بقية الـsuite.

**النتيجة: PROVEN للآلية.** المساران مساران تنفيذيان مختلفان تحت Intent واحد وSealed Contract واحد وSuccess Contract واحد، وكلاهما بلغ Intent Fulfillment:

| المقياس | Path A | Path B |
| --- | --- | --- |
| Action Success | step 3 و4 نجحا | step 5 و6 نجحا |
| Path Termination | {1,2,3,4} | {1,2,5,6} |
| Intent Fulfillment | اجتماع واحد مطابق للمعايير الثلاثة | اجتماع واحد مطابق للمعايير الثلاثة |
| Task State | COMPLETED | COMPLETED |

وكذلك: لا خطوة من ذراع واحدة تظهر في سجل الذراع الأخرى، ولا `action_id` مشترك بينهما، ولكل مهمة `ir_program_id` واحد و`ir_fingerprint` واحد، والذراع تُشتق من Evidence دائم لا من النموذج.

**عيب اكتُشف وأُصلح.** كان التحقق من أن الـCondition تقرأ step قد ظهر على المسار يستخدم صيغة «يوجد مسار واحد» بدل «كل المسارات». برنامج تقرأ فيه `branch-3` نتيجة step 2، بينما ذراع `1 → 3 → branch-3` لم ينفّذ step 2 قط، كان يُبنى ويعمل ويصل حتى بوابة موافقة الكتابة في التقويم. استُبدل الفحص بفحص domination صريح، ورُفض البرنامج قبل تنفيذ أي action. القاعدة نفسها موصوفة معياريًا في `docs/kai-ir-spec-v0.md` §8.3.

**الحد المحدد بدقة — INCONCLUSIVE.** المساران اللذان قِيْسا يختلفان في control flow فوق capability واحدة. أما الخيار على مستوى الـprovider — «اختيار Slot 1» مقابل «اختيار Slot 2»، أو method A مقابل method B داخل capability واحدة — فغير قابل للتعبير بمفردات الحقائق المغلقة. وهذا الحد معرَّف معياريًا في `docs/kai-ir-spec-v0.md` §4.4.5؛ ما هنا سجل قياس، لا مصدر سلطة.

لم تُضَف أي primitive: لا Loops ولا Parallel ولا Graph مفتوح ولا نوع عقدة جديد ولا نوع حقيقة جديد ولا تغيير في Gateway أو Policy أو Approval أو Action identity. وبقي `ResultNode` Terminal Marker بلا أي صلاحية.

## 9. ResultNode

ResultNode ليس حاليًا مصدر الحقيقة لـIntent Fulfillment.

دوره المناسب هو:
- Terminal Path Marker؛
- تمثيل بنيوي لنهاية المسار؛
- Outcome مسجل عند الحاجة.

ولا يجب أن يصبح State Machine ثانية أو أن يقرر Policy أو Approval أو Task State أو Completion من تلقاء نفسه.

## 10. Fulfillment وCompletion

يجب فصل:

1. **Action Success:** نجح الـAction مباشرة.
2. **Path Termination:** انتهى المسار.
3. **Intent Fulfillment:** تحقق ما طلبه المستخدم وفق Contract وEvidence.
4. **Task Lifecycle State:** الحالة الرسمية للمهمة.

```text
Action Success ≠ Path Termination ≠ Intent Fulfillment ≠ Task State
```

### 10.1 القرار: Fulfillment بالطبقات، وسلطة القرار في KAI

السلطة على الـFulfillment **مقسّمة بالطبقات**، والقرار النهائي يبقى في KAI:

```text
Contract
  يحدد السؤال
      ↓
Evidence
  يقدم الحقائق
      ↓
Fulfillment Evaluator
  يفسر السؤال داخل مجاله
      ↓
Fulfillment Verdict
  حكم حتمي ثلاثي
      ↓
Task State Machine
  تسجل النتيجة
```

العلاقة الشكلية:

```text
fulfilled(Intent, Sealed Contract, Durable Evidence)
  -> { FULFILLED, NOT_FULFILLED, INDETERMINATE }
```

وشرط إعادة الاشتقاق:

> `COMPLETED` ⟺ `Verdict == FULFILLED`. لا شرط إضافي.

**الربط الملموس: `fulfillment_profile`.** اسمُ المُقيِّم ليس اختيارًا ضمنيًّا يُستنتج من مجموعة الأدوات ولا من اسم الـGoal؛ هو حقل في الـSealed Contract، مكتوب مرة واحدة عند الـSeal ومحفوظ مع العقدة، ويقرأه الـRuntime عند التسوية لا غير:

```text
TaskContractInput.fulfillment_profile : Literal["calendar_meeting", "gmail_send"]   # مُغلَق
        ↓ persist
tasks.fulfillment_profile                                             # محفوظ
        ↓ read at settlement
FulfillmentVerdict -> Task State Machine
```

المُقيِّم يُختار من **الـContract المحفوظ**، فلا يستطيع `Plan` ولا ردّ النموذج ولا مسار الاسترجاع أن يوجّهوا القرار إلى مُقيِّم آخر؛ المهمة المنقطعة والمهمة التي اكتملت يقرأان الحقل نفسه فيحصلان على المُقيِّم نفسه. والقيمة مقيَّدة بمفردين اليوم، فإضافة مجال آخر هي **تعديل في العقد** لا بحث في سجل.

**«صالح في الـschema» لا يعني «قابل للختم الحيّ».** المفردان في النوع هما مدى مفردة الـschema، لا مدى التشغيل الحيّ:

```text
FulfillmentProfile = Literal["calendar_meeting", "gmail_send"]   # schema-valid (tasks/schemas.py)
        ↓
LIVE_SEALABLE_PROFILES = frozenset({"calendar_meeting"})         # الختم الحيّ (tasks/service.py)
        ↓
gmail_send -> schema-valid  ->  NOT live-sealable
```

`create_task` يرفض أي `fulfillment_profile` خارج `LIVE_SEALABLE_PROFILES` بـ`UnlicensedFulfillmentError`، عند الكتابة الوحيدة إلى `Task.fulfillment_profile`. فـ`gmail_send` يمرّ عبر طبقة الـschema ويُرفض عند الختم الحيّ، وهما بوابتان منفصلتان (§10.2).

**لماذا حقل مسمّى لا اشتقاق.** الاشتقاق (`goal` فيه «اجتماع» ⟹ مُقيِّم التقويم) يجعل اختيار المُقيِّم وظيفةً لـLLM غير مقيَّدة، فيعود السؤال الأصلي: من يقرر معيار الحكم؟ الاسم الصريح يجيب: الـContract.

**لماذا ليست سلطة واحدة.** لو ملك الـContract دلالة «تم» وحده، لكان عليه تفسير `success_criteria` وهو نص طبيعي، أي يحتاج إلى نموذج، أي انتهاكًا لـ«Model proposes؛ Authority decides» ولحتمية القرار. ولو ملك المجال الدلالة كاملة، صار الـFulfillment ثقة موزّعة: كل مجال مرجع تدقيق مستقل، ولا يبقى طرف واحد يعيد اشتقاق الحكم، ويتحرك Lifecycle بنطاقات لا تملكها KAI. الطبقة تحفظ الأمرين معًا: سؤال محدد ومقروء، وقرار واحد قابل للتدقيق وإعادة الاشتقاق.

### 10.2 حدود كل طبقة

| الطبقة | تجيب عن | لا تجيب عن |
|---|---|---|
| Sealed Contract | ما هي المعايير | هل تحققت |
| Durable Evidence | ما الذي حدث فعلًا | ماذا يعني |
| Fulfillment Evaluator | هل تحققت المعايير في مجالها | ما حالة المهمة |
| Task State Machine | ما حالة المهمة الآن | هل تحققت المعايير |

قواعد ملزمة:

- **الـContract يسأل ولا يجيب.** يحدد المعايير، ولا يحمل دلالتها التنفيذية، ولا يُعدّل بعد الـSeal.
- **الـEvaluator لا ينقل حالة.** يُخرج حكمًا فقط؛ الانتقال الحصري إلى `COMPLETED` يبقى في `Task State Machine`.
- **الـEvaluator حتمي وبلا آثار جانبية.** لا نموذج، ولا شبكة، ولا قراءة حالة غير محفوظة — وإلا اختلف الحكم عند إعادة الاشتقاق.
- **الـEvidence هي المخزون الوحيد.** الحكم يُشتق من Evidence كاملة، لا من هوية step أو مسار بعينه؛ لذلك ذراعان مختلفان تحت Contract واحد ينتجان حكمًا واحدًا.
- **رخصةُ الملف ≠ مرساةُ النيّة.** الختمُ يُرخّص ملف fulfillment للتنفيذ الحي (أيُّ سؤاليُّ يُطرح)، بينما المرساةُ هي ما يربط نتيجةَ المُقيِّم بما أراده المستخدم فعلًا (أيُّ قيمةٍ يقرّر عليها). البوّابتان منفصلتان: اجتيازُ إحداهما ليس اجتيازَ الأخرى، ورخصةُ الملف بلا مرساة قاعدةٌ مرفوضةٌ (§10.10).

### 10.3 INDETERMINATE لا تحتاج حالة Lifecycle جديدة

ثلاثية الحكم ضرورية لأن «لم تتحقق المعايير» و«لا يمكن الحسم بعد» مسألتان مختلفتان، وطمسهما يحوّل عدم اليقين إلى فشل.

```text
FULFILLED      -> COMPLETED
NOT_FULFILLED  -> FAILED
INDETERMINATE  -> REQUIRES_ATTENTION
```

`REQUIRES_ATTENTION` موجودة أصلًا، وقابلة للانتقال إليها من `VERIFYING`، وغير نهائية. ولا حاجة لإضافة حالة جديدة. ومتى يحدث `INDETERMINATE`: المعيار نفسه غير قابل للفصل من Evidence المتاحة، أو Evidence الناقصة كانت سبب عدم اليقين لا نتيجة جزم.

### 10.4 ما يجب أن يبقى مستحيلًا

> لا يجوز للنموذج أن يعلن أن نية المستخدم تحققت. ولا يجوز لأي Node أو Provider أو Model.

- لا يعلن النموذج الـFulfillment، ولا يحدّده من `Intent` أو `Plan` أو `ResultNode`.
- لا ينقل الـEvaluator حالة المهمة، ولا يختار حالة، ولا يعيد توجيه المسار.
- لا يقرأ الـEvaluator إلا Evidence محفوظة، فيبقى الحكم قابلًا لإعادة الاشتقاق بعد أي Crash.
- لا يكفي `ok` خاص بـAction واحد لإثبات الـFulfillment؛ Action Success ليس دليلًا على المعنى.
- لا يُبدَّل الـEvaluator المعتمد بعد تسجيل حكم دون أثر تدقيق يربط الحكم بمُقيِّمه.
- لا يُقرأ الحكم المسجَّل ولا `evaluator_version` لإعادة تقرير حالة؛ يُعاد اشتقاقه من الأدلة، فما يخرج من الاشتقاق هو الصحيح.

### 10.5 وضع التنفيذ الحالي

ما هو مثبَّت اليوم، بالمسار الحقيقي:

- **الربط قائم وصريح.** `fulfillment_profile` حقل مطلوب في `TaskContractInput`، محفوظ في `tasks`، ومقروء من صف الـTask عند التسوية. الـRuntime يوزّع عليه عبر مفردات مغلقة (`calendar_meeting`)، ويرفض أي قيمة خارجها بدل أن يشغّل مُقيِّمًا افتراضيًا.
- **المُقيِّم دالة نقية في مدخلات محفوظة.** `FulfillmentInput` سجل مجمَّد (`frozen`) يحمل نافذة الاجتماع المحفوظة، والهويات المُحلَّلة، وسجل Evidence الدائم فقط. لا جلسة، ولا مهمة، ولا ردّ نموذج، ولا مدخل حيّ — والغياب بنيويٌّ لا اتفاق.
- **الحكم ثلاثي.** `FulfillmentVerdict = {FULFILLED, NOT_FULFILLED, INDETERMINATE}`، والفصل إلى Lifecycle منفصل عنه تمامًا: `FULFILLED -> COMPLETED`، `NOT_FULFILLED -> FAILED`، `INDETERMINATE -> REQUIRES_ATTENTION`.
- **الحكم دالة في مجموعة الأدلة لا في ترتيبها.** أدلة الـFulfillment تُنتقى أولًا (المحاولات المؤهلة: `calendar.create_event` نجحت، وتحقّق منها، ومعها `event_id` من المزوّد)، ثم تُقيَّم **المجموعة** كلها. القاعدتان مُفصَلتان عمدًا ولا تختاطان:
  - على **المجموعة**: وجودية — «هل **يوجد** اجتماع مؤهَّل يحقق المعايير؟».
  - على **اجتماع واحد**: عَطْضية — `all()` على معاييره الثلاثة، لا على المجموعة.

  فـ`Verdict = f({E1..En})`، لا `f(first record)`. والاختيار غير قائم على موضع السجل: لا ممثِّل يُنتقى ولا دالة كسر تعادل، فالترتيب لا يُستشار في أي موضع. والمجموعة الفارغة **جواب** لا فراغ: `NOT_FULFILLED`، لا `all([]) == True` ولا `INDETERMINATE`.
- **القرار ما زال في KAI.** يوجد موقع قرار واحد ينقل إلى `COMPLETED`، و`VERIFYING` هي الحالة الوحيدة التي تسمح بذلك. `_settle_verification()` هي الدالة الوحيدة التي تستهلك الحكم وتنتقل؛ والمُقيِّم دالة تُعيد حكمًا ولا تملك جلسة.
- **نقطة القرار واحدة للمباشر والاسترجاع معًا**، فالمهمة المنقطعة والمهمة التي اكتملت يُحسمان بالشيفرة نفسها على المدخلات نفسها.
- **أثر التدقيق مكتوب، وغير مُطاعم.** `FulfillmentOutcome` سجل مجمَّد واحد يحمل `{profile, version, verdict}` معًا، ويكتبه `_settle_verification()` على `RuntimeExecution` **قبل** الانتقال، فيلتزم trio التقييم والحالة في commit واحد. والثلاثية **أثرٌ لا سلطة**: لا شيء يقرأها لتقرير الحالة، وكل تسوية تعيد الاشتقاق وتكتب فوقها. اختبارٌ يزرع `NOT_FULFILLED` مخالفًا للأدلة يثبت أن الاشتقاق الجديد هو الذي يفوز.
- **هوية المُقيِّم ثابتة ودلالية.** `CALENDAR_MEETING_EVALUATOR_VERSION = "calendar_meeting:v1"` — ثابت مكتوب بيد بشري، ليس بصمة commit ولا طابعًا زمنيًا ولا مخرج نموذج. يصف **دلالةَ المُقيِّم** لا نتيجته، فالحكم الواحد لا يغيّر الإصدار (نفس الإصدار يغطي الأحكام الثلاثة)، وإعادة الاشتقاق بعد Crash تُعطي الإصدار نفسه. ويأتي `profile` من الفرع الذي شغّل المُقيِّم، فلا يمكن تسجيل هويةٍ لدلالةٍ لم تُشغَّل.
- **التاريخ لا يُدَّعى.** الأعمدة الثلاثة `nullable` وبلا backfill: صفٌّ بلغ التحقق يسجّل الثلاثية، وصفٌّ توقّف قبله أو وُجد قبل الهجرة يبقى `NULL`. و`NULL` تعني «غير مسجَّل» لا «لم يعمل مُقيِّم» — ولو كُتبت نسخةٌ مُعاد بناؤها لادَّعت أصلًا لم يُسجَّل، وقد تكون خاطئة: الدلالات التي كانت تعمل قبل إعادة التسمية كانت «الشاهد الأول»، وهذا تحديدًا ما تكشفه الهوية.
- **النموذج لا يدخل في دائرة الحكم.** لا حقل للـ`fulfillment_profile` في `PlanProposal`، و`extra="forbid"` ترفضه؛ والمُقيِّم يقرأ نافذةَ مُفهَّمةٍ **محفوظة ومختومةًا عند التقديم**، لا مخرجات نموذج حيّة. الأصلُ مودَّل، لكن المُفقَد هو مشتقّ يُعاد كله عند التسوية.
- **عميل خارجي لا يدّعي `COMPLETED`**؛ الانتقال محجوز للسلطات الحتمية.

ومتى يحدث `INDETERMINATE` فعليًا؟ **لا مسار حيّ في هذا المجال يُنتجه**: كل فحص في `evaluate_calendar_meeting` مقارنة حتمية على قياسات محفوظة، والـRuntime لا يدخل `VERIFYING` إلا بعد نجاح كل إجراء، فالسؤال له جواب دائمًا في هذا المجال. قيمة `INDETERMINATE` مُنفَّذ وموصول من آلة الحالات، ويُختبر بتدخّل مباشر على `_fulfillment_outcome`؛ وهذا **خاصية في المجال** لا ثغرة في الربط. وهي تُحفظ في السجل مع `evaluator_version` كما تُحفظ أي حالة أخرى، فلا يضيع الحكم لأنها نادرة.

وعُمل في هذه الخطوة على **المعنى** نفسه، لا على موضعه:

- **المعنى صار نموذجًا مُصفَّفًا ومختومًا، لكن للنطاق الواحد فقط.** `SuccessCriteria` في `runtime/fulfillment.py` هو السلطة التي يقرأها المُقيِّم: `profile` + حزمة `calendar_meeting` مجمَّدة (`frozen`) و`extra="forbid"`، فيها `window` (الكائن المختوم نفسه، لا نسخة منه) و`required_attendees`. و`FulfillmentInput` صار `{criteria, evidence}`: لا سيناريو ولا هويات — لأن المُقيِّم لم يعد يستنتج الشروط. **والـprose بقي** كله: يُحفظ، ويُقارن verbatim مع الخطة، ويصل إلى التلقين. والسلطة صارت للـtyped لا للنص. والمعيار الثالث من الـprose («event created») **ليس حقلًا**: هو سؤال الدليل لا مُعامل، وجعله مُعاملًا كان سينشئ شيئًا قادرًا على مخالفة الدليل.
- **الختم مُوروث لا مكرَّر.** العقد يُختم عند `submit` **قبل** الفهم، فلا نافذة بعد — وهذا ترتيب حقيقي لا نقص. والمعايير تُختم من صفَّي `RuntimeExecution` المختومين: `scenario` (النافذة) و`identities` (المُحلَّلون)، وكلاهما مُلتزَم قبل تشغيل أي أداة ولا يُعاد حسابه أبدًا. وهي دالة نقية عليهما، فـ**لا migration ولا عمود جديد ولا backfill ولا صفّ تاريخي ناقص**. والتقييم صار `f(sealed_criteria, relevant_evidence_set)`، ومدخلاته لا تقبل جلسة ولا نموذجًا.
- **`required_attendees` لا يُرفض إن كان فارغًا.** الحالة محسومة سلفًا: `NOT_FULFILLED` (`test_an_unresolved_attendee_is_not_fulfilled`). ورفضُها عند الختم يحوّل حكمًا محسومًا إلى فشل تشغيل — تغيير دلالة لا تحقق. وكذلك التطبيع: `casefold` وتخطّي ما لا بريد، **بنفس** تعبير الكود السابق؛ و`str(...)` لقيمة غير نصية تبقى تحويلًا لا رفضًا. فالسكوت عن البيانات التالفة سلوكٌ مقصود مثبَّت.
- **لا رفض جديد إلا ما هو مستحيل الوصول أصلًا.** الرفض الفعلي: حقل خارج المجال (`extra="forbid"`)، ونافذة لا تمرّ على `MeetingWindow`، ومعايير تسمّي `profile` لا تحمل له حمولة. **وهذا الحد مقصود**: إضافة تحقق فوق بيانات كانت تُنتج حكمًا تنقلها إلى فشل غامض في الـruntime.
- **`title` ليس معيار نجاح.** إنه داخل النافذة، والمُقيِّم لا يقرأه قط؛ والترقية إلى حقل معيار ستكون اختراع شرط لم يكن في المجال.
- **ولا سجل مُقيِّمين، ولا لغة معايير.** لا registry ولا بحث بالاسم ولا شجرة boolean: `for_calendar_meeting()` هو الطريق الوحيد إلى حزمة، و`SuccessCriteria` يرفض أي `profile` لا يحمل له. ومجال ثانٍ تعديلٌ مقصود لهذا النموذج، كما أن `FulfillmentProfile` نفسه قائمة مغلقة.

وما هو غير قائم بعد، مفتوحًا صراحةً:

- **نموذج دلالي عام، ومقصود عدم بنائه الآن.** النموذج الحالي واجهة `Profile` واحدة مع حمولة واحدة. ومن نفّذ شجرة شروط عامة، أو predicate مسجَّلًا، أو معايير يكتبها نموذج، يكون قد قرّر قرارًا معماريًا لم يُطلب. **هذا ليس نقصًا في هذه المرحلة** بل حدٌّ متعمَّد: أي تعميم يحتاج موضعًا جديدًا للسلطة، وهذا يحتاج قرارًا مستقلًا.
- **مُقيِّمان مكتوبان، لا سجلّ.** ~~`Literal` من مفرد واحد~~ **بعد التجربة**: `FulfillmentProfile = Literal["calendar_meeting", "gmail_send"]`، ما زال `Literal` مغلقًا: لا سجلّ مُقيِّمين، ولا بروتوكول، ولا Skills، ولا مسار تسجيل يضيف مجالًا ثالثًا. والقيم مغلقة عمدًا، فالمجال الثاني تعديلٌ صريح في العقد. ولهذا فـ`FulfillmentProfile` في `tasks.schemas` هو مصدر النوع الوحيد، و`calendar_meeting:v1` و`gmail_send:v1` معرَّفان في `fulfillment.py` لا في سجل قابل للتسجيل. والتوسيعةpartir من مفردين ليس لغة معايير: انظر §10.7.
- ~~عدم تماثل في تأهيل المحاولة~~ **مُغلق**: صار للمعنى مكان واحد صريح. `kai/runtime/evidence.py` يعرّف «المحاولة المؤهَّلة» تعريفًا واحدًا: محاولة `calendar.create_event` خرجت `EXECUTION_SUCCEEDED`، و`ok`، ومتحقَّق منها، وتحمل `evidence["event_id"]` نصًّا غير فارغ. والنتيجة `QualifyingCreation` مجمَّدة فيها `provider_event_id` و`arguments` فقط، **بلا معرِّف محاولة** (لا `step_order` ولا `request_id` ولا `ir_action_id`): الشاهد يحدِّده ما يشهد له، لا موضعه في السجل، ومعرِّف بلا قارئ ليس إلا شيئًا ثانيًا قد يخالف الصف الذي يدّعي وصفه. والدالة `qualifying_creation()` **نقيّة وكاملة**: لا I/O، ولا جلسة، ولا حالة مهمة، ولا سجل آخر، ولا شبكة، ولا مسمّى؛ فهي دالة في محتوى السجل الواحد وحده. `evaluate_calendar_meeting` و`_created_event_id` يقرآن هذا الحدّ نفسه عبر `qualifying_creations()`، فلم يبقَ تعريف ثانٍ مخفيّ في helper، ومسار الاسترجاع وإعادة الاشتقاق يقرآن الحدّ نفسه لأنهما يقرآن `RuntimeExecution.evidence`.
- **والقرار في `event_id` صريح، وهو المرجع `evidence`.** السبب في نموذج التنفيذ نفسه: `evidence` هي ما يُعيد نشره **حدّ التحقّق** بعد إعادة تأكيد عقد الأداة — `ContractVerificationEngine` يرفض أن يُبلّغ `verified` لأداة إنشاء ما لم يحمل `event_id` استخدمته القراءة-بعد-الإنشاء (`READ_AFTER_CREATE`) — أي فهي ادّعاء **عمّا أُثبِت**، بينما `data` هي حمولة المزوّد كما يعيدها الـadapter ويمرّرها الـGateway في كل الحالات دون استشارة ذلك العقد إطلاقًا، أي هي ادّعاء **عمّا قاله المزوّد**. فـ`data.event_id` وحده **غير كافٍ** لإثبات الـFulfillment: لا في الـevaluator ولا في استخراج الـid، ولا يوجد fallback. والقيمتان متساويتان في الـadapter الوحيد الذي يكتبهما اليوم، لكن التساوي مصادفة لا عذر: القاعدة تُطبَّق سواء تطابقتا أم لا، لأن قراءة `data` كانت ستُدخل إلى مجموعة الشهود هويةً لم يقف خلفها حدّ التحقّق — أي ادّعاءً يُقدَّم كدليل. ويبقى الإغلاق محصورًا في `calendar_meeting`: فمعرّفات مزوّدين أخرى تفتح مسألة **متعدد الهويات** (§17)، لا هذا البند.
- **لا هوية مُقيِّم مسجَّلة ولا إصدار.** ~~`RuntimeExecution` لا يسجّل أي `verdict` ولا `evaluator_version`~~ **مُغلق**: `RuntimeExecution` يسجّل الآن `{fulfillment_profile, evaluator_version, fulfillment_verdict}`، وكلها `nullable` وبلا backfill. ويبقى مفتوحًا: أن تُوسَّع الدلالات مستقبلًا بغير ترحيل، فسجلٌّ يعبر هذا الحد سيقرأ إصدارًا واحدًا لا إصداراتًا.
- **`FulfillmentInput` لا يحمل السيناريو ولا الهويات بعد.** أثره: سجل التسوية لا يستطيع اليوم أن يوثّق «أي ضيوف» دون الرجوع إلى الصف. مقبول الآن لأن الصف نفسه هو المصدر الوحيد، لكنه سقفٌ قابل لإعادة النظر عند تعدّد المجالات.

لذلك: **الربط صار صريحًا، والحكم صار ثلاثيًا، والفصل إلى Lifecycle منفصل، والحكم صار دالة في مجموعة الأدلة، وصار لكل حكم هويةٌ مكتوبة، وصار معنى النجاح نموذجًا مُصفَّفًا يُقرأ بدل نص، وصار معنى «المحاولة المؤهَّلة» معرَّفًا في موضع واحد يُقرأ بدل تكراره — لكن دلالة الـFulfillment العامة ليست محسومة بعد.** ولا يجوز إعلان النموذج العام مكتملًا، ويجب إبقاء الفارق بين «الربط قائم» و«الدلالة عامة» مفتوحًا. إغلاق ذلك الفارق الأخير لا يُشترَط أن يكون معرَّفًا لـ`calendar_meeting` فحسب، بل مُعمَّمًا على مجالات لا مجالَ منها واحد بعد.

### 10.6 مراجعة الإغلاق الدلالي (KAI Fulfillment Semantic Closure Review v1)

**الحكم: `FULFILLMENT SEMANTICS — CALENDAR SLICE` = `CLOSED`.**

مغلق **داخل** `calendar_meeting`، لا مُعمَّمًا. والحكم قولان منفصلان:

* **مغلق**: يوجد تعريف **واحد** لـ«المحاولة المؤهَّلة» (`kai/runtime/evidence.py::qualifying_creation`)، و`event_id` مقروء من `evidence` وحده، و`SuccessCriteria` مختومة هي مرجع المعنى، والحُكم deterministic وdurable وقابل لإعادة الاشتقاق من durable state وحده، ولا يقرأ الـevaluator ولا يُغيّر أي lifecycle، ولا يوجّه المعنى إلى أي موضع في السجل.
* **غير مغلق**: أي ادّعاء بأن البنية **مُجرَّبة** على مجال ثانٍ. لا يوجد مجال ثانٍ، فليست هناك تجربة، فلا يجوز ادّعاءُ ما لم يُختبر.

#### 10.6.3 حدود `calendar_meeting`

* **أ — خاص بالمجال بالتصميم**: `MEETING_CREATION_TOOL`، وشرط تضمين الحاضرين، واحتواء النافذة، و`CalendarMeetingCriteria`، و`calendar_meeting_criteria`، و`evaluate_calendar_meeting`، و`CALENDAR_MEETING_EVALUATOR_VERSION`. بقاؤها هنا هو ما يجعل المجال مقروءًا.
* **ب — تنفيذ الشريحة العمودية**: `FulfillmentProfile = Literal[...]`، وغلاف `SuccessCriteria` بحمولة إجبارية واحدة، ومُصيِّر `_payload_matches_profile`، والفرع المغلق في `_fulfillment_outcome`، وكون `evidence.py` باسمٍ محايد ومحتوى خاص بالمجال. **هذه لا تُعمَّم بالتخمين**؛ إن ظهر مجال ثانٍ فهذه مواضع ستُعدَّل صراحةً.
* **ج — عيب دلالي محتمل (مُبلَّغ، غير مُصلَح)**: المعنى المُتحقَّق منه هو أن **بداية** الحدث داخل النافذة؛ ولا شيء في السلسلة يقيّد **نهايته** ولا مدته، بينما الـprose تقول «event fits the requested time window» وهي أعمّ. هذا سلوكٌ محفوظ من قبل النموذج، وتغييرُه يغيّر أحكامًا، فليس في نطاق هذه المراجعة.
* **د — غير معروف**: هل يحتاج مجال ثانٍ هويةً واحدة أم أكثر، وهل تعامل مجموعةُ الشهود بـ`∃` أم بشيء آخر، وهل `INDETERMINATE` قابل للوصول خارج `calendar_meeting`.

#### 10.6.4 Decision Memo: المجال الثاني (مقترحٌ آنذاك، ونُفِّذ في §10.7)

المجال المقترح: **إرسال رسالة** عبر `gmail.send`. وهو ليس افتراضيًا: الأداة **موجودة في المستودع** ومكتملة (`READ_AFTER_SEND`، وهوية `message_id` في `evidence`، و`verified = not mismatches`، وقراءة-بعد-إرسال تقارن المُرسِلَ والمستقبِلَ والعنوان و`SENT`)، لكنها خارج `SLICE_ALLOWED_TOOLS` و`SLICE_CAPABILITIES` ولا شريحة لها.

1. **المجال**: إرسال رسالة واحدة إلى جهة محدَّدة.
2. **لماذا**: بنية المزوّد متطابقة مع `calendar.create_event` في كل ما يهم المعنى: أداة واحدة، هوية مزوّد واحدة، عقد قراءة-بعد-كتابة، `data` مقابل `evidence` منفصلان. فهو أرخص اختبار ممكن للقول إن البنية تتبع الشكل لا الاسم.
3. **السؤال الدلالي الذي سيختبره**: هل ينجو معنى «شاهد واحد لهوية واحدة» حين لا يكون الشاهد «إنشاء»، وحين يعرض المزوّد **هويتين** (`message_id` و`thread_id`) في `evidence` نفسه؟
4. **ما الذي لن يختبره**: التعميم على أكثر من مجال، ولا لغة معايير عامة، ولا تغيّرًا في Gateway أو Policy أو Approval أو Identity أو KAI-IR أو آلة الحالات.
5. **الأدلة المتوقعة**: سجل `gmail.send` واحد، `outcome=EXECUTION_SUCCEEDED`، `ok`، `verified`، `evidence.message_id` نصًّا غير فارغ — أي نفس القالب تمامًا.
6. **الهوية**: اثنتان متاحتان؛ `message_id` هي المرشح الطبيعي للسلطة، و`thread_id` هي منافس حقيقي. هذا هو الحافة الفعلي للتجربة.
7. **هل `qualifying_creation` ينطبق**: **لا** بالمعنى الاسمي، ونعم بالبنية. فالتجربة لا تعيد استخدام الدالة؛ تسأل هل صيغة «شهادة مجمَّدة بحقلين: هوية المزوّد + وسائط الطلب» نفسها هي حدٌّ قابل لإعادة الاستخدام أم مصادفةٌ باسم مجال.
8. **معايير القبول**: تعريف مؤهَّل ثانٍ مستقل؛ `message_id` من `evidence` وحده بلا fallback إلى `data`؛ المقياسان منفصلان كما في الأول؛ عدم قراءة موضع السجل؛ إعادة اشتقاق متطابقة بعد الانهيار؛ عدم قبول أي تغيير في KAI-IR أو آلة الحالات أو Gateway.
9. **المخاطر**: أن ينزلق التنفيذ إلى abstraction عامة (لغة معايير، سجل مُقيِّمين) قبل أن يثبت التكرار دلاليًا؛ أو أن يُنسخ `evidence.py` كاملًا فيتشكّل تعريف ثانٍ لا رابطه.
10. **خارج النطاق عند الكتابة**: كل ما سبق — كانت التجربة **مؤجَّلة** ولم يُكتب لها كود. ونُفِّذت بعد ذلك على النحو المسجَّل في §10.7؛ فالحكم فيها على الكود لا على النية.

**`Stable Core Milestone`**: البنية الحالية **مستقرة**، والتصميم مقصود. قرار تأجيل التعميم ليس نقصًا: المجال الثاني لم يثبت بعد، وإثباته بتجربة حدوده أضيق من إثباته بعموم مبنيَّ مقدمًا.

### 10.7 تجربة المجال الثاني: `gmail.send` (Second-Domain Experiment)

السؤال الذي وُضعت له التجربة: **هل تظهر دلالاتُ `calendar_meeting` مرةً ثانية بشكلٍ حقيقي في مجالٍ مختلف، أم أن اختلاف المجال يكشف الحاجة إلى abstraction مختلفة؟**

**النتيجة في سطر واحد**: **الشكلُ نجا، والمضمونُ لم ينجُ.** أي أنَّ `∃` و`∧`، وغيابَ الاعتماد على ترتيب السجل، وغيابَ الاعتماد على التكرار، والمجموعةَ الفارغة، و`durable outcome`، و`evaluator identity`، وإعادةَ الاشتقاق: **دَعَامٌ متطابقة**. بينما **الـprojectionَ والهويةَ والمعاييرَ تغيّرت كلها**، ولم تُشتق من الأولى.

وحكم التعميم: **partially proven** — الربط مُثبَت على مجالين، ودلالة الـFulfillment العامة **لم تُثبَت** بعد.

> **تصحيح §10.9:** سطر «why that count» في هذا الجدول كُتب أوّل الجولة مبدئيًّا بصيغة «مرفوضان لأن الطلب نسخةٌ منهما»، ثم صُحِّح في الجولة نفسها إلى ما هو مكتوب الآن. الصيغة الأولى **خاطئة**: الطلب يحمل العناوين نفسها عبر `create_intent_args`. انظر §10.9.1.

**قرار الهوية، وهو جوهر التجربة**: `gmail.send` ينشر هويتين في `evidence`، فاختيرت `message_id` ورُفض `thread_id`، والسبب دلاليّ لا برمجيّ:

* `message_id` هو العنوان الذي صدرت عليه القراءة-بعد-الإرسال فعلًا (`client.get_message(message_id=sent.message_id)`)، و`verify_send` يشترط `readback.message_id == sent.message_id` — أي مساواة بين جوابَي مزوّد. وهو 1:1 مع المحاولة.
* `thread_id` اسم **تجميع محادثة**، والخيط يحوي رسائل سابقة وردودًا ورسائل من مرسلين آخرين. السماحُ به يجعل الشاهد **لا يعرّف شاهدًا**: محاولتان في خيط واحد تتشاركان `thread_id` واحدًا، فينهار ما يميّز محاولةً عن أخرى. ونموذج التحقّق القائم يوافق: `_missing_contract_evidence` يشترط `message_id` وحده، و`verify_send` يعامل `thread_id` كوجودٍ لا كمقارنة.
* ولا يوجد fallback إلى `data`، وهنا الرفض **أقوى بنيويًّا** من رفض `event_id`: فـ`GmailAdapter._send` لا يملأ `evidence` إلا حين نجح القراءة-بعد-الإرسال، فالمحاولة غير المتحقَّقة لا تملك هوية في أي حقل — أي أن الثغرة غير موجودة أصلًا. ومع ذلك فالقاعدة مكتوبةً صريحةً، لأن اليوم الذي يبدأ فيه adapterٌ بكتابة المعرّف في `data` هو اليوم الذي يجب أن يكون الرفض حاضرًا سلفًا.

#### 10.7.3(ج): المعايير، ولماذا كانت **حقلًا واحدًا** لا اثنين

الفرق الجوهري بين المجالين، وهو **نتيجةٌ مُصحَّحة بالفحص المباشر للكود** لا افتراض:

* **تحقُّق كلا المجالين يقارن القراءةَ بعد العملية بالـ`request` الذي أنتجها، لا بالـIntent.** `verify_event` يفحص `title` و`start` و`end` و`timezone` و`date` و`start_time` و`end_time` **و`attendees`**؛ و`verify_send` يفحص `message_id` و`thread_id` و`SENT` والمُرسِلَ والمُستقبِلَ **و`subject`**. فـ`verified=True` يعني في المجالين معًا: **أن المزوّد أعاد طلبنا** — أي ادّعاءٌ عن الطلب، لا عن الـIntent.
* **وتحقّقُ الـCalendar أوسعُ فعلًا** من تحقّق الـGmail (ثمانية حقول مقابل ستّة، ومنها الحضورُ والتاريخ)، ومع ذلك يحمل **حقلَي معايير** مقابل حقلٍ واحد. فمدى التحقّق **لا** يفسّر الفرق.

**إذن ماCriterion الحقلُ لأجله هو مصدرٌ مختومٌ يُقاس عليه الطلب.** يُكتب حقلُ معيار حيث يجد المُقيِّم قيمةً مختومةً تجيب عمّا لا تجيبه حقولُ الطلب وحدها:

1. **صفُّ الهويّات المختوم `row.identities`** — قد يوفّر سلطةَ استقلالٍ (independence authority) لقيمةٍ من قيم المعايير المشتقّة، لكنّه لا يُثبت بذاته نيّةَ المستخدم: السجلّ يبلّغ عنه ولا يُثبته، والعمود الدائم هو مصدره.
2. **مجموعةٌ لا يستطيع الطلب حملَها** — لأن الطلب يستقبل **لحظةً واحدة** بعينها، بينما الـIntent طلب **نافذةً** (مجالُ الـCalendar وحده).

**وهذا ما كان مكتوبًا هنا أوّلًا، وهو مصحَّح (§10.9.1)**: كان مكتوبًا أنّ الصفة الأولى «لا يحملها الطلب إطلاقًا». و`create_intent_args` يملأ `args["attendees"]` من الهويات المختومة نفسها التي تُختم منها المعايير — **فالطلب يحمل العناوين نفسها**، و`verify_event` يقارن حضور القراءةَ بعد العملية بالطلب **بمساواة مجموعة**. أي أنّ حقلَ `required_attendees` على المسار الحيّ الوحيد **مُحَمى فيه التحقّق**، ولا يستطيع سجلٌّ من ذلك المنتج أن يفشل في هذا الحقل ويظل شاهدًا. والصيغة الصحيحة أضيق: الحقل يبقى لأنّ السجلّ **غير ملزَم** بأن يكون كُتبه ذلك المنتج، وعمودُ `identities` هو سلطة العنوان لا `args`.

**وكلُّ رفضٍ في المجالين له سببُه المعلن، لا سببٌ واحدٌ مشترَك:**

* `subject` يقارنه `verify_send` بالطلب، **ولا يوجد مصدرٌ مختومٌ له** في العقد ولا في الفهم ولا في أي عمود — فمعيارٌ له يقرأ الطلب في نفسه. **و`title` في `CalendarMeetingCriteria` مرفوضٌ لسببٍ مختلف** يجب ألّا يُستعير: مصدرٌ مختومٌ لـ`title` **موجود**       (`MeetingWindow.title`)، والمزوّد يقارنه بالطلب، ولا يذكره نثرُ المعايير المختوم — فالسبب هناك **غيابُ تقريرٍ لا غيابُ مصدر**.
* `body` لا يقارنه `verify_send` إطلاقًا، ولا يحمل الـIntent متنًا مختومًا مستقلًا — فمعيارٌ **لا تستطيع الأدلةُ المتحقَّق منها أن تُحققه أبدًا** يُعطّل كل إرسال. (لا يُضاف حقلٌ إلى المعايير لمجرّد وجوده في النثر.)

**ولماذا ليست المعايير tautology في المجالين معًا**: مصادرُها صفوفٌ مختومة **مستقلة عن الأدلة** — `scenario.window` و`row.identities` — و`arguments` المحاولة هي ما تُقارَن عليه. ولو خُزِّنت المعايير من `arguments` نفسها لكان المُقيِّم يقرّر trivially ولا يستطيع أن يقول `NOT_FULFILLED` أبدًا. هذه هي النقطة التي يفشل فيها التعميم السريع.

| استيراد حدّ الـwitness بدل تكراره | ✅ نعم | مع **وحدة مختلفة** لكل مجال |
| `∃` على المجموعة، `∧` داخل الشاهد | ✅ نعم | `∧` بـحقلٍ واحد هنا، وحقلين هناك |
| independence عن الترتيب والتكرار | ✅ نعم | |
| `INDETERMINATE` غير قابل للإصدار | ✅ نعم | لـسببٍ بنيويّ، لا اتفاق |
| **projection واحدة تخدم المجالين** | ❌ **لم تثبت** | `QualifyingCreation` ≠ `QualifyingSend`، بلا base مشترك |
| **مصدرُ intent مختوم واحد** | ❌ **لم يثبت** | النافذةتُ gmail لا معنى لها؛ ومعايير gmail لا تقرأ `scenario` أصلًا |
| **عدد حقول المعايير** | ⚠️ **مختلف** | 2 مقابل 1، لسبب دلالي (§10.7.3) |
| **عدد هويات المزوّد** | ⚠️ **مختلف** | 1 مقابل 2، ومعيار الاختيار دلاليّ |

**وهذا هو جواب «هل ظهرت abstraction مشتركة حقيقية؟»**: **لا، بعدُ.**ليس لأن البنية لم تتكرر — البنية تكررت — بل لأن هناك **ثلاثة** مواضع كان يجب أن تكون مشتركة ولم تكن: الـprojection، ومصدر الـintent المختوم، وعدد الحقول. وقاعدة الكود لذلك: تكرار الشكل بين مجالين **دليل على إمكانية التعميم، لا إثباتٌ له**؛ و`evidence.py` و`send_evidence.py` لا يندمجان إلا بدليلٍ ثانٍ ثالث.

#### 10.7.5(ه): حالة `INDETERMINATE` غير قابلة للإصدار، ومُسجَّلة لا مخترَعة

`evaluate_gmail_send` لا يُصدر `INDETERMINATE`، لسببٍ بنيويّ: كل فحص مقارنةٌ قابلة للحسم على scalars دائمة، فلا شيء فيه غير محسوم. enum يبقى ثلاثة، وهذا المجال يُنتج اثنين.

لكن هناك حالةٌ **تبدو** وكأنها تحتاج القيمة الثالثة، ويجب تسجيلها لا اختراعها: **إرسالٌ قبلَه المزوّد لكن فشلت القراءة-بعد-الإرسال.** عندها `verified=False` و`evidence` فارغ، فالسجل ليس شاهدًا والحكم `NOT_FULFILLED` — **مع أن الرسالة ربما سُلِّمت فعلًا**. وهذا صحيح تحت السؤال المطروح فعلًا («هل تثبت أدلةٌ متحقَّقٌ منها durable أن الـIntent تحقّق»)، وهو نفسه جوابُ `calendar_meeting` حين يكون الحدث المنشور غير مقروء.

**والفرق أن gmail يجعل المخاطرة مرئية**: إعادةُ المحاولة بعد إرسالٍ غير متحقَّق منه قد تُسلِّم الرسالة مرتين، وهذا **أثرٌ غير قابل للتراجع**. وهو حجّةٌ حقيقية لقيمة «تعذّر الحسم» تختلف عن «لم يتحقّق» — لكن تصميمها يحتاج قرارًا في سياسة إعادة المحاولة وفي سؤال الإنسان، لا قيمة enum جديدة. لذلك هي **مؤجَّلة**، ولم تُخترع هنا حالة اصطناعية تبقى غير قابلة للإصدار.

#### 10.7.6(و): حدود التجربة — ما لم يُنفَّذ منها

التجربة أُجريت على **طبقة المعنى**، لا على تشغيل رسالة من طرفٍ إلى طرف. والسبب قيدٌ صريح في النطاق: تشغيلُ `gmail.send` حيًّا يحتاج فهمًا ثانيًا في `UnderstandingOutput` وجدولَ قدراتٍ ثانيًا في الـtranslator وبرنامج KAI-IR للإرسال — وكلها **ممنوعة في هذه المرحلة** (توسيع KAI-IR ممنوع، وشريحةُ الـtranslator تقتصر على `calendar_meeting`).

فما هو **مُنفَّذ ومُختبَر**: الربط (profile → criteria → مُقيِّم → نسخة) على مستوى `_fulfillment_outcome`، ومسارُ الاسترجاع يصل إلى الفرع نفسه من الصف نفسه.

وما هو **مؤجَّل**: أن يقود الـruntime مهمةً فعليًا باسم `gmail_send`، فـ`SLICE_FULFILLMENT_PROFILE` ما زال `"calendar_meeting"` لكل مهمة تقودها الشريحة، ولم يُرخَّ هذا القيد ليُرضي التجربة — بل سُجِّل مؤجَّلًا. أي أن `gmail_send` **قابلٌ للعقد، غير قابلٍ للقيادة**، والفرق بينهما مقصود ومُعلَن.

#### 10.7.8(ي): وُتي نُثبت بها، ووتي لم يثبت

**مُثبَت على مجالين**: (١) العقد المختوم يختار المُقيِّم، (٢) معايير typed لا تُقرأ منها نثرًا، (٣) دلالاتُ المجموعة `∃`+`∧` مع استقلال تام عن الترتيب والتكرار، (٤) المجموعة الفارغة قرارٌ لا فراغ، (٥) `evaluator_version` ثابت، (٦) النتيجة المحفوظة أثرٌ لا سلطة، (٧) إعادة الاشتقاق تحسم ما ضاع.

**غير مُثبَت**: (١) أن هذه البنية **تظهر في مجالٍ ثالث**، (٢) أن الـprojection يمكن أن تكون مشتركة، (٣) أن عدد حقول المعايير قابل للتنبؤ، (٤) أن هوية المزوّد تُختار بقاعدةٍ واحدة، (٥) أن «الشكل» هو ما تتبّعه البنية بدل الاسم — فمجالان اثنان أسماؤهما مختلفان وكودهما متشابه، وهذا ما يُسمّى **توافقًا، لا إثباتًا**. **(٦) والتعميم العام: `unproven`.**

`Stable Core Milestone`: **`partially proven`، لا `proven`.** ومعيار الترقية إلى `proven` ليس **مجالًا ثالثًا ناجحًا**، بل **دليلٌ دلالي** على أن **المواضعَ الثلاثة** التي تعذّر دمجها (الـprojection، ومصدر الـintent المختوم، وعدد حقول المعايير) لها قاعدةٌ واحدة. ولم يثبت هذا بعد، فقد بُني في هذه التجربة §10.7.3 لأجله تحديدًا.

### 10.8 Cross-Domain Fulfillment Semantic Analysis

جولة تحليل بين المجالين، غرضها الإجابة عن سؤالٍ واحد: **ما الذي يبقى صحيحًا مهما اختلف المزوّد؟**

**نتيجة البوابة الأولى — الـEvidence Projection.** يوجد **مفهومٌ دلالي واحد** مشترك: **هويةُ المزوّد التي تصلح أن تكون شاهدًا** يجب أن تأتي من إعادة نشر حدّ التحقّق (`evidence`)، لا من حمولة الـadapter المتسلسلة في `data`. وهو مُثبَت في المجالين، ويؤيّده الكود القائم نفسه: `_missing_contract_evidence` يشترط `event_id` و`message_id` على السواء. أمّا **إسقاطُ السجل** — أي أيّ السجلات تُقبل — فليس مشتركًا: الأداة مختلفة، وحقل الهوية مختلف ومختارٌ على أسبابٍ مختلفة، ومجموعة الحقول المطلوبة للتقييم مختلفة. فالحكم: **مفهوم الهوية مشترك، ودالةُ qualification دومانية.** فـH1 جزئيٌّ فقط، وH2 صحيحٌ في الإسقاط.

**نتيجة البوابة الثانية — مصدر الـIntent.** النمطُ مشترك والTYPEُ واحد: كلاهما يقرأ `row.identities` المختوم والمحلول مسبقًا، **بلا migration**. لكنّ المعنى دومانيّ: في الـCalendar هم ضيوفٌ يجب حضورهم، وفي الـGmail هم مُرسَلٌ إليهم. و`UnderstandingOutput` **لا يملك حقلَ مُستقبِل** أصلًا — `\"schedule_meeting\"`, `guests`, `window` لا غير — فإسقاطُ `guests` على معنى «مُرسَل إليه» **افتراضٌ تجريبيّ غير مُثبَت**، لا قاعدة. ويقرأ فرعُ الـGmail `scenario` **لا** (`service.py`: «`scenario` is deliberately not read»)، بينما يقرأه الـCalendar لـ`window`: فالمصدرُ نفسُ الصفّ، والتحويلُ مختلف.

**نتيجة البوابة الثالثة — عدد الحقول.** الجدول أعلاه. وقد **صُحِّح في هذه الجولة تبريرٌ خاطئٌ كان في الكود**: كان مكتوبًا أن تحقّق الـCalendar «يثبت فقط أن الحدث مقروء» وأن تحقّق الـGmail «يقارن بالطلب». والفحص المباشر لـ`verify_event` ينفي ذلك: فهو يقارن `title` و`start` و`end` و`timezone` و`date` و`start_time` و`end_time` **و`attendees`** — أي **أوسع** من `verify_send`. فمدى التحقّق لا يفسّر فرقَ عدد الحقول. والقاعدة الصحيحة هي ما في §10.7.3 بعد تصحيحها: **يُكتب حقلُ معيار حيث يجد المُقيِّم مصدرًا مختومًا لا يجيبه الطلب وحده** — أي نافذةً يستقبل الطلبُ منها لحظةً واحدة بعينها، وعمودَ `identities` الذي هو سلطةُ العنوان الذي يبلّغه السجل. **وهي لا تشرح الرفضين معًا**، فقد سُحبت القاعدةُ التي كانت تشرحهما معًا («الطلبُ ليس نسخةً مما يقاربه»)، ورُفض `subject` لغياب المصدر المختوم، ورُفض `title` لغياب التقرير رغم وجود المصدر — **اختلافٌ في السبب، لا قاعدةٌ واحدة**. والاختبار الذي كان يُذكَر شِاهدًا على القاعدة المصحَّحة `test_a_criterion_is_stated_only_where_the_request_is_not_a_copy_of_it` **أُعيد تسميته ووُسِّع** إلى `test_no_refusal_rests_on_the_request_being_a_copy_of_the_intent`.

**نتيجة الـQuantifier.** `∃ شاهد ∧ المعايير داخل شاهدٍ واحد` صمدت في المجالين تحت كل الحالات الخمس المفحوصة: شاهدان صالحان، صالح+غير صالح، تكرار، أدلةُ دخيلة، ومجموعةٌ فارغة. والشرط **قاعدةٌ دلاليةٌ حقيقية** لا إعادةُ استعمالٍ للنمط: لولا النطاقُ الواحد لكان منطقيٌّ أن يُعطي شاهدٌ الحضورَ وآخرُ النافذةَ حكمًا واحدًا، والفحصُ ينفي ذلك صراحةً (`A+B → NOT_FULFILLED`).

**ملاحظة مهمّة — انحلالُ الحدّ الواحد.** في `gmail_send` الحقلُ **واحد**، فالتقارب `∧` **لا يمكن أن يُخرَق أصلًا**: لا معيارَ ثانيَ يُقسم بين شاهدين. فالثابت S4 (المعايير داخل شاهدٍ واحد) **مُثبَتٌ ومحمولٌ في `calendar_meeting`**، و**قبلٌ في `gmail_send`**. وهذا سببٌ إضافي لبقاء `partially proven`: المجالان لا يثبتان الشيءَ نفسه بالوزن نفسه.

**نتيجة قرار الـAbstraction.** **لا استخراجُ abstraction الآن.** المفهوم المشترك (انظر أعلاه) واحدٌ فقط، ولا ينطبق إلا على قراءة الهوية، وحقلُه ومصدرُه وأداتُه دومانية، ودورُه في الـlifecycle واحدٌ بالطريقتين لكنهما لا يلتقيان بعد لأن `gmail_send` غير حيّ. فالبنية الصحيحة هي **مبادئُ دلاليةٌ مشتركة + إسقاطاتٌ ومُقيِّماتٌ دومانية**، وهي الحالة القائمة فعلًا. وأي استخراجٍ الآن سيكون تعميمًا على **مجالين**، وهو ما تعني كلمة `unproven`.

### 10.9 تدقيق الـProvenance: من أين تأتي كل قيمة في `SuccessCriteria` (Intent-to-SuccessCriteria Provenance Review)

جولةٌ على مستوى **القيمة** لا المجال: لكل حقلٍ في الحزمتين — من أي صفٍّ مختومٍ يُقرأ، وما التحويل الذي يمرّ به، وأيًّا من الأشياء الأربعة هو، ومَن يحسمه. الغرضُ من ذلك التمييزُ بين «المعنى» و«الشكل»، لأن §10.7 و§10.8 أثبتا **الشكل** في مجالين ولم يفحصا **المصدر**؛ ومصدرُ القيمة هو ما يحدّد إن كان التعميمُ قائمًا أم مفترضًا.

**والخلاصةُ التي لا تتغيّر**: `GENERALIZATION = partially proven`، و`guests → recipients = EXPERIMENTAL / UNPROVEN`، ولا استخراجَ لـabstraction، ولا تغييرٌ في دلالات الـCalendar.

#### 10.9.1 التصحيح الجوهري: القاعدةُ المسحوبة، وما الذي حلّ محلّها

كان في §10.7.3 و§10.8 وفي `fulfillment.py` جملةٌ واحدة تشرح رفضَ حقلين ووجودَ حقلين: **«يُكتب حقلُ معيار حيث لا يكون الطلب نسخةً مما يقاربه»**. وقد سقطت، لأن الفحص المباشر **`create_intent_args`** — وهو المنتجُ الحيّ الوحيد للطلبات — يملأ `args["attendees"]` من `identities` المختومة نفسها التي تُختم منها المعايير:

| | ما كان مكتوبًا | ما يقوله الكود |
| --- | --- | --- |
| `row.identities` | «لا يحمله الطلب إطلاقًا» | الطلبُ **يحمله**: `args["attendees"]` منه مصدرُه |
| الأثر | الحقلُ هو ما لا يبلغه التحقّق | `verify_event` يقارن الحضورَ بالطلب **بمساواة مجموعة**، فالحقلُ **مُحَمى فيه التحقّق** على ذلك المسار |
| `subject` | «نسخةٌ من الـIntent نفسه» | **لا مصدرَ مختومًا له أصلًا** — لا في العقد ولا في الفهم ولا في أي عمود |
| `title` | «مرفوضٌ للسبب نفسه بالضبط» | مصدرُه المختوم **موجود**، والمزوّد يقارنه، ونثرُ المعايير لا يذكره: **غيابُ تقريرٍ لا غيابُ مصدر** |

فالنتيجةُ قاسيةٌ في اتجاهٍ ومتساهلةٌ في آخر: **الرفضان لم يكونا للسبب نفسه**، فالقاعدةُ التي كانت تربطهما معًا كانت **أضيق من أن تصدق**، والسببُ الواحد المتخيَّل كان **مزيجًا من سببين مختلفين**. والصيغةُ الصحيحة أضيق بكثير: **يُكتب حقلُ معيار حيث يجد المُقيِّم مصدرًا مختومًا لا تجيبه حقولُ الطلب وحدها** — أي نافذةً يستقبل منها الطلبُ لحظةً واحدة بعينها، وعمودَ هويةٍ هو سلطةُ العنوان الذي يبلّغه السجل.

**والأهمّ — ما الذي بقي يحمل حقلَ الـCalendar الثاني**، وهو نتيجةٌ لم تكن مُتوقَّعة: **النافذة هي الحقلُ الوحيد الذي يستطيع المسارُ الحيُّ أن يُسقطه**، و`required_attendees` مُحَمى فيه. والدليلُ مبنًى من المترجِم الحقيقي والمُحقِّق الحقيقي لا من fixture: مزوّدٌ يبلّغ بفتحةٍ خارج النافذة → `pick_slot` يختارها → الطلبُ يحمل تاريخًا خارجَ النافذة → `verify_event` **يمرّ** → ومع ذلك `NOT_FULFILLED`، لأن النافذةَ المختومة وحدها هي ما يقول لا. الاختبار: `test_the_range_is_the_only_criterion_the_live_path_can_fail`.

#### 10.9.2 خريطة المصدر، حقلًا حقلًا

| القيمة | تُقرأ من | التحويل | صفّها | مَن يحسمها |
| --- | --- | --- | --- | --- |
| `profile` | `tasks.fulfillment_profile` | قيمة مغلقة، بلا تحويل | **B** — من العقد المختوم | العقد وحده يُنتقي المقيِّم |
| `window` | `RuntimeExecution.scenario.window` | يُختم كما هو، بلا نسخ | **A** — محتوى نيّة، مختوم بعد الفهم | الفهم الختمي؛ لا النثر |
| `required_attendees` | `RuntimeExecution.identities[*].email` | `casefold` + تخطّي الفارغ | **C + D** — ناتجُ محلّل + وصفُ التحقّق | صفُّ الهوية، لا `args` |
| `required_recipients` | `identities` نفسها، نفس التعبير | نفس التحويل | **C + D** — والنيّةُ **غيرُ مؤسَّسة** | لا شيء: لا مصدرَ نيةٍ مختومًا |

`identities` — لا مرّة واحدة في الحزمتين، بل **دفترُ مفاتيح واحد**: النداءان يبدآن من `identities` وبنفس تركيب العناوين `str(item['email']).casefold() for item in identities if item.get('email')`، فلا يوجد في `src/` أي producer ثانٍ يبني معايير gmail. وهذا **دليلُ تعميمٍ محتمل، لا إثباتٌ له**.

#### 10.9.3 سلطة الهوية: `row.identities` دمجٌ لا سجلُّ نية

الصفُّ ليس أثرًا للنيّة ولا أثرًا للتنفيذ، بل **الحاجزُ بينهما** — ولهذا يُخطئ تسميةُه بأيٍّ منهما. نصفُه الأوّل (`name`) قراءةُ النموذج للهدف؛ ونصفُه الثاني (`email`) ناتجُ محلّل الهوية من بيانات مزوّدٍ حيّة أو تلميح ذاكرة؛ والاثنان معًا يُختمان قبل أي أداة. **والمعايير تقرأ النصف الثاني فقط**، فـ:

* الاسمُ لا يبلغ المعايير: ضيفٌ كتبه النموذج `Ahmed Alkhatib` ينتج **الحقلَ نفسه**؛ وضيفان يحلّان إلى عنوان واحد ينتجان **عنصرًا واحدًا**. فالمعيار يقول **أيُّ عناوين يجب أن تكون حاضرة**، لا **أيُّ أشخاص طُلبوا**.
* `status` و`confidence` **لا يبلغان المعايير**: `_POSITIVE_IDENTITY` بوّابةُ تشغيلٍ لا شرطُ نجاح. وال-runtime **يمتنع عن التشغيل أصلًا** إن لم يُحلَّ كل ضيف إلى هوية موجبة، فحيث وصل الحكمَ فقد أدّى الدليلُ عمله. وحملُهما إلى المعايير يعني شرطًا لا يراه المقيِّم، ويجعل حلًّا أدنى ثقة يبدو إنجازًا أضعف — وهو سؤالٌ آخر.
* فالوصفُ الأمانةُ لـ`required_attendees` ليس «الضيوف الذين طلبهم المستخدم»، بل **«العناوين التي أنتجها محلّلُنا للضيوف الذين سمّاهم النموذج»**.

#### 10.9.4 العقد المختوم يُسهم بـ`profile` وحده

وهذه خطوةٌ يتجاوزها كلُّ من §10.7 و§10.8، لأنّها غائبة عنهما لا مناقضة لهما: **لا builderَ للمعايير يقرأ `goal` ولا `success_criteria`**. ما يُقرأ من العقد هو `fulfillment_profile` وحده؛ وما يُقرأ لـ`window` هو **النافذةُ كما فهمها النموذج**، المختومة في `scenario`. فمهمّتان بعقدين متعارضين تمامًا في `goal` وفي نثر معاييرهما تُحسمان **بصورة متطابقة** من صفّ الفهم نفسه. وهذا **الموضعُ الصحيح** لمقيِّمٍ حتميٍّ لا يُقاد بالنموذج — وهو أيضًا الوصفُ الأمانةُ لمكان «ما طلبه المستخدم»: **ليس في العقد**، ولا يُقرأ منه.

**فائدةٌ ثانوية، وهي التي تجعل الفارق مهمًّا**: أيُّ تغييرٍ في نثر العقد بعد الختم لا أثرَ له بالمعنى الحتميّ، **وكذلك `goal`**. فالفارق المتبقّي بين الجولات ليس في **حساسية المعنى** للنصّ — فهي في كليهما صفر — بل في **السلطة**: أيُّ مصدرٍ مختومٍ يجيب عن أيّ سؤال. وهذا يجعل النقاشَ كلَّه سؤالَ **مصدر** لا سؤالَ **حساسية**، وهو ما لم يُصنَّف قبل هذه الجولة.

#### 10.9.5 `guests → recipients`: يُثبَّت كافتراضٍ بنيويّ، ويُترك مفتوحًا

لا يوجد في المستودع **مصدرُ نيةٍ مختوم** لمستقبِلٍ في أي مكان: `UnderstandingOutput` حقوله `{intent, guests, window}`، و`intent` محصورٌ في `"schedule_meeting"`، و`guests` قائمةُ أسماء عرضِ 1–5، و`extra="forbid"` يمنع أن يضيف النموذج حقلًا، ولا يُذكر في `UNDERSTANDING_SYSTEM_PROMPT` لفظُ `recipient` ولا `email`، ولا عمودَ في `RuntimeExecution` يحمل مستقبِلًا. **فلا يمكن برمجةُ التكافؤ بقراءة الكود — وهذا هو سبب بقائه `EXPERIMENTAL`.**

وإضافةً إلى ذلك: فرعُ الـGmail **لا يقرأ `scenario` أصلًا**، ومرحلةُ الهوية تشترط `scenario.guests` في المجالين، واسترجاعُ `VERIFYING` يرفض غياب السيناريو برسالة `cannot verify: no understanding on record` رغم أن مُقيِّمَ gmail لا يستعمل النافذة. فالمعايير تُختم من صفٍّ **لم يُقرأ له معنى في هذا المجال**، لأنّ معناه يختلف فيه.

**وهل يكفي مجالٌ ثالث؟** لأغراض **عدد الحقول** والتنبؤ بالبنية: نعم، هذا هو الشاهدُ الناقص. ولأغراض **`guests → recipients`**: **لا**، فمجالٌ ثالثٌ لا يضيف دلالةً مختومة لمصدرٍ لم يُختم أصلًا. الترتيبُ الصحيح: **أوّلًا** يُختم نيةُ مستقبِل، **ثم** يُختبر التكافؤ، **ثم** يُقاس مجالٌ ثالث. والاختبار `test_the_gmail_branch_never_reads_a_meaning_for_its_identity_row` و`test_a_gmail_contract_is_sealable_but_the_runtime_never_seals_one` يُثبّتان الحدَّين معًا.

**وأثرُ ذلك في باب الترخيص (§10.10)**: `required_recipients` = **لا مصدرَ نيّةٍ مختومًا** = **غيرُ مرخّصٍ للتسجيل الحي حاليًا**. `gmail_send` يبقى في المفردة، ويُرفض عند `create_task` — الكتابة الوحيدة على `Task.fulfillment_profile` — حتى يُختَم نيةُ مستقبِلٍ ويقرّر عليه مُقيِّمه.

**وتُشدَّد هذه النتيجة في §10.10.2**: غيابُ الحقل ليس نقصًا في التسمية بل **سلسلةَ غيوبٍ مترابطة** — لا مشهدَ مختومًا يسأل السؤال، ولا علاقةَ بين أي قيمةٍ مختومة وبين كلمات المستخدم، ولا ذاكرةً خارج حدِّ الفهم، ولا مفتاحَ ربطٍ بين القيمة المختومة والدليل الوحيد الذي يقرأه مُقيِّمُ gmail. فإضافةُ حقلٍ منفردٍ لا تُصلح أيًّا منها.

### 10.10 Anchor Requirement for Live Sealing (متطلّب المرساة للتسجيل الحي)

المبدأ المصادَق عليه (§10.7.3 و§10.9) كقاعدةِ ترخيصٍ صرّحتها الجولة التنفيذية:

> “A Success Criterion may contain derived values, but a domain whose every criterion value is derived from execution-time resolution is not fulfilling an intent; it is reporting its own self-consistency. Such a profile must not be sealed for live use until at least one criterion value has a sealed user-intent source that its evaluator decides on.”

نطاقه **رخصةُ التسجيل الحي فقط** — أي ما يُتاح لملف fulfillment ليُختم ويُقاد إلى `FULFILLED → COMPLETED`. لا يُغيّر شيئًا في دلالات المعايير، ولا في `calendar_meeting` ولا في `gmail_send` ولا في التسوية.

قواعد البند:

* **العضوية في `FulfillmentProfile` ليست إذنًا للتسجيل الحي.** المفردة أوسعُ من الترخيص، والقِسْمان مسألتان مختلفتان: الأول يعيّن *أيُّ سؤالٍ يُطرح*، والثاني يعيّن *هل يُتاح طرحُه حيًّا*.
* **`gmail_send` يبقى في المفردة**، ولا يُرخَّص له حاليًا: كلُّ قيمةٍ في معياره مشتقّةٌ من resolve وقت التنفيذ، وليس له مصدرُ نيّةٍ مختومٌ يقرّر عليه مُقيِّمه (§10.9.5).
* **الحدُّ التنفيذي هو `create_task`** — الكتابة الوحيدة على `Task.fulfillment_profile` — قبلَ أيّ ترسيخٍ للصف. وليس في التسوية، لأن الحكمَ يُحتسب هناك فيكون قد فات أوان الرخصة.
* **الإنفاذ ساكنٌ وعلى مستوى الملف** (`LIVE_SEALABLE_PROFILES` مفردةٌ مغلقة + فحصٌ في `create_task`)، لا فحصٌ لمعايير runtime: المعايير غير موجودة وقتَ الختم أصلًا.
* **أهلية الملف المدرَج صيانةٌ صريحة** بالكود (إدراجٌ في المفردة المغلقة) وباختبارات القيد — وهي مسؤوليةُ اختبارٍ لا إثباتٌ مشتقٌّ (§20).
* **ختمُ نيةِ مستقبِلٍ يبقى شرطًا مسبقًا لأي عمل Gmail مستقبلي** (§10.9.5 و§10.9.6): لا يُفتح `gmail_send` للتسجيل الحي قبله.
* **مصدرُ المستقبِل على وجهٍ رسميّ**: لا قيمةَ معيارٍ لمستقبِلٍ نيّةٌ مختومةٌ إلا إذا كانت إسقاطًا لصفّ الفهم (§10.9.5)، ودوامُ العنوان المشتقّ في `row.identities` لا يرفعه إلى طبقة النيّة — فدوامُ القيمة يغيّر أثرَها لا سلطةَ مصدرها (§10.10.1 و§11).

القاعدةُ المرافقة التي لا تُبادَل بالعكس: وجودُ حقلٍ مختومٍ لا يكفي؛ المطلوبُ حقلٌ **يقرّر عليه المُقيِّم** — فـ`MeetingWindow.title` موجودٌ مختومٌ ولا يقرّر عليه شيء منها (§10.9.2).

#### 10.10.1 نموذجُ «النيّة المختومة للمستقبِل» (Sealed Recipient Intent)

يعرّف هذا البندُ دلالةَ «مستقبِل» في KAI بحيث تصير حكمَ ترخيصٍ قابلًا للتنفيذ (يُختبر في مجموعة ‏`tests/test_recipient_intent_provenance.py` قسم ‏5)، لا وصفًا يُقرأ مرتين:

* **أ— التمثيل (Intent representation)**: «مستقبِل» ليس قيمةً واحدةً يحملها كلامُ المستخدم. هو ثلاثةُ قيمٍ متمايزةٌ تحت لفظٍ واحد: الاسمُ الذي يذكره (١)، والعنوانُ المستخرَج من الذاكرة وتُشرِّعه جهاتُ الاتصال (٢)، والعنوان الذي يسجّله طلبُ الأداة (٣). الأولى وحدها يمكن أن تكون نيّةً مختومةً، والثانية حلٌّ، والثالثة دليلُ طلب. والمستودعُ اليوم لا يختم الأولى أصلًا: `UnderstandingOutput` حقوله `{intent, guests, window}`، و`extra="forbid"` يمنع حقلَ مستقبِل، ولا يذكر الـprompt لفظَها (§10.9.5).
* **ب— حدّ الحل (Resolution boundary)**: العنوانُ يُنتَج خارج طبقة النيّة — تلميحُ ذاكرة، ثم استعلامُ محلِّل، ثم شرطُ جهات الاتصال، ثم `row.identities[*].email`. دوامُ ذلك الصفّ في القاعدة يجعل الحلَّ أثرًا دائمًا لا نيّةً مطلوبة؛ فالتخزينُ لا يعيد تصنيف القيمة (§10.10 و§11).
* **ج— قاعدةُ الختم (Sealing rule)**: قيمةُ معيارٍ «نيّةٌ مختومة» إذا وفقط إذا كانت **إسقاطًا للفهم المختوم** وكان على مُقيِّمها أن **يقرّر عليها**. لذلك `calendar_meeting` مرخَّصٌ لأنّ `window` إسقاطُ `scenario.window` ويقرّر عليه مُقيِّموها، و`gmail_send` غيرُ مرخَّصٍ لأنّ `required_recipients` كلُّه طبقةُ حلٍّ. الاختبار `test_live_sealing_is_granted_only_where_a_criterion_value_comes_from_sealed_user_intent` يجعل هذه القاعدة حكمًا آليًّا على التوقيعين وعلى ما يقرؤه المُقيِّمان.
* **د— دلالاتُ الطبقات الأربع (Identity semantics)**: تتمايز أربعُ طبقاتٍ لا تندمج: الاسم (فهمٌ مختوم) ≠ العنوان (ذاكرة/جهاتُ اتصال، `CONTACT_MATCH`) ≠ سجلُّ الاتصال (حقيقةُ المزوّد غايتُها الشرطُ لا الإمداد) ≠ `to` في الطلب (صدًى يقارنه التحقّق). معيارٌ يختم على (١) هو الشكلُ المرخَّصُ المستقبليّ؛ ويُمنع أن تتظاهر (٢)/(٣)/(٤) بأنها (١) مهما طال سكونُها في صفّ مختوم.
* **هـ— التوافق (Compatibility)**: ترخيصُ `gmail_send` يستلزم تمثيلًا مختومًا جديدًا لـ«من يتلقّى» تنتجه مرحلةُ الفهم، يُسقَط في المعايير، ويقرّر عليه المُقيِّم، مع بقاء خريطة الاسم→العنوان حلًّا مختومًا كما هي اليوم. ذلك **تعديلُ عقدٍ** يُعكس خصائصَ مُثبَّتةً حاليًا (حقول المخطط، ومفردة الـprompt، وعدم قراءة الفرع للسيناريو)، ويستلزم توسيعَ مفردة النيّة خلف `Literal["schedule_meeting"]` وتوسيعَ جدول القدرات.

**حكمُ هذه الجولة: ‏Design-only.** لا تغييرَ في الكود المنتج؛ `LIVE_SEALABLE_PROFILES` وفحصُ `create_task` والبناءان والمُقيِّمان كما هي. `gmail_send` يبقى في المفردة، ملفًّا مختومًا **غيرَ مرخَّصٍ للتسجيل الحي**، حتى يُختم تمثيلُ «من يتلقّى» ويقرّر عليه مُقيِّمه.

وتُشدَّد هذه النتيجة في §10.10.2: **البند (هـ) كان يسجّل أن الترخيص «يستلزم» تعديلَ عقد، ولم يحدّد أيّ تعديلٍ بالضبط** — وهذه الجولة تحدّده، وتبيّن أن شرطَ التحديد هو أيضًا شرطُ عدم التمكين الآن.

#### 10.10.2 ما الغائب بالضبط: سلسلةُ غيوبٍ لا حقلٌ ناقص

`UnderstandingOutput` حقوله `{intent, guests, window}`. قلنا إن «مستقبِلٍ لا يُذكر» — وهذا صحيحٌ لكنه غيرُ كافٍ، لأن جوابَ «ما الذي نضيفه» لا يُشتقّ من قائمة حقولٍ ناقصة. الجوابُ يشتقّ من **أربعةِ غيوبٍ مترابطة**، كلٌّ منها يمنع التمثيلَ حتى لو أُضيف الحقل:

| | الغياب | ما الذي لا يمكن أن يُقال | الشاهد |
| --- | --- | --- | --- |
| **غ١** | **لا مشهدَ مختومًا يسأل السؤال** | لا يمكن تمثيل «من يتلقّي» أصلًا: `intent` محصورٌ في `Literal["schedule_meeting"]`، وحقلا المشهد الآخرين تقويميان (قائمةُ مدعوين + نافذةُ تواريخ). حقلُ مستقبِلٍ يُضاف اليوم إمّا فارغٌ دائمًا، وإمّا تقريرٌ ثانٍ لـ`guests` | `kai/runtime/schemas.py` · `UnderstandingOutput` |
| **غ٢** | **لا علاقةَ بين قيمةٍ مختومة وكلمات المستخدم** | لا يمكن التمييزُ بين «المستخدم قال X» و«النموذجَ افترض X»، فلا يصحّ أن يُبنى عليها عنوانٌ يُسلَّم لمزوّد. البوابةُ الحتميةُ الوحيدةُ اليوم في هذا المسرح هي نافذةُ التاريخ في الماضي، وهي عن حقل الـCalendar لا عن اسمٍ أو عنوان | `kai/runtime/understanding.py` · `understand_scenario` |
| **غ٣** | **لا ذاكرةً خارج حدّ الفهم** | لا يمكن تسميةُ قيمةٍ مختومةٍ «نيّةً» إن كان أصلُها في ذاكرة. والذاكرةُ **داخل** كتلة فهم النموذج اليوم: `_memory_notes` ينتقي `PERSON` و`PREFERENCE`، و`_user_datablock` يمرّرها حرفيًّا داخل `<preferences>`. فـ«النموذجُ أنتج العنوان» و«الذاكرةُ أنتجت العنوان» لا يُميَّز بينهما عند حدّ النموذج | `kai/runtime/service.py` · `_memory_notes` · `kai/runtime/understanding.py` · `_user_datablock` |
| **غ٤** | **لا مفتاحَ ربطٍ بين القيمة المختومة والدليل** | شاهدُ الإرسال يحمل `args` بمفاتيحها الثلاثة `to` و`subject` و`body` بالضبط، والحكمُ containment بين `args["to"]` والمجموعة المختومة. فلا durable value أخرى في الدليل تحمل اسمًا — فالقيمةُ التي يُقرّر عليها مُقيِّمُ gmail **لا بدّ أن تكون عنوانًا أو لا شيء** | `kai/runtime/send_evidence.py` · `QualifyingSend` · `kai/runtime/fulfillment.py` · `_send_satisfies_criteria` |

**وثلاثةُ استخلاصاتٍ تغيّر صياغة التصميم كلَّه:**

1. **غ٤ يقرّر شكلَ التمثيل قبل أن يُبحث عنه.** أيُّ تصميمٍ يبدأ من «نحفظ الاسمَ كما قاله المستخدم» يفشل في (د) فورًا: اسمٌ لا مفتاحَ ربطَ له، فـ`required_recipients` إما فارغٌ أو مرفوض. **والعكسُ صحيح**: العنوانُ وحده هو المفتاحُ الممكن. فالسؤال ليس «أيُّ تمثيلٍ يحفظ النيّة» بل «أيُّ قيمةٍ مختومةٍ *هي* الجملةُ التي كتبها المستخدم، وبأيّ سندٍ».
2. **غ٣ يهدم التحكّمَ بالـprompt.** أيُّ مُستخرِجِ مستقبِلٍ في هذا المسرح يستطيع أن يقرأ عنوانًا من `<preferences>` ويختمه، وعند حدّ النموذج لا فرق بين ذلك وقراءته من `<goal>`. فالسندُ لازم يكون **فحصًا حتميًّا** — «كلُّ عنوانٍ مُسنَدٍ يجب أن يَرِد حرفيًّا داخل `<goal>`» — لا تعليمةً في نصّ الطلب. والفحصُ موجودٌ كمبدأ في المسرح (النافذةُ لا تبدأ في الماضي)، فالقاعدةُ قابلةٌ للتوسعة لا مخترَعةً من العدم.
3. **غ١ يجعل التمثيلَ تعديلَ عقدٍ لا إضافةَ حقل.** أيُّ تنفيذٍ اليوم يُنتج مخرجًا «اجتماعًا» يحمل داخله دعوى إرسال، أو يرفض «الإرسال» أصلًا. وهذا هو الحدُّ الذي مُنِعَ تجاوزُه في هذه الجولة: راجع §10.10.4.

#### 10.10.3 التمثيلُ المقترح، والبدائلُ التي رُفضت ولماذا

التصميمُ الذي يفيّ بالشروط هو **«عنوانٌ مُسنَدٌ إلى Goal»** (Grounded Address):

```text
goal:  "send the plan to alice@example.com before friday"
                  └──────┬──────┘
                        │
        understand_scenario ──فحصٌ حتميّ: العنوانُ واردٌ حرفيًّا في <goal>؟
                        │  نعم ──► UnderstandingOutput.recipients = ["alice@example.com"]
                        │  لا  ──► UnderstandingFailed
                        ▼
                    الختمُ في scenario  ──►  recipients تُسقَط في GmailSendCriteria
                        │                        (بلا خريطةِ أسماء، وبلا row.identities)
                        ▼
                    evaluate_gmail_send: required_recipients ⊆ {args["to"]}
```

خصائصُه الأربع، ولكلٍّ منها ما يُبطل البديلَ الذي يلغيها:

| الخاصية | لماذا لازمة | ما يُبطله |
| --- | --- | --- |
| **مُسنَد** — كلُّ عنوانٍ يَرِد حرفيًّا في `<goal>` | العنوانُ هو جملةُ المستخدم، لا اجتهادُ أحد | «Alice» ← `alice@example.com`: ترقيةُ اسمٍ إلى عنوانٍ بلا سند |
| **عنوان** — لا اسم | غ٤: لا مفتاحَ ربطَ لغير العنوان | معيارٌ على `Alice` = `NOT_FULFILLED` دائمًا، مهما كانت صيغتُه |
| **ليس جهةَ اتصال** — يبقى `CONTACT_MATCH` شرطًا على الإرسال | القيمةُ دعوىٌ على المزوّد أن يُلبّيها، لا ما يُغذّيها | جعلُ المطابقةِ مصدرًا: تعودُ الذاكرةُ إلى طبقة النيّة |
| **ليس حسابَ المستخدم** — لا مستقبِلٌ افتراضيّ | تفريعُ الحساب في المحلِّل يُعيد عنوانَ الحساب، وهو اختراع | «راسلني/نفّذ» ← عنوانُ الحساب بصمت |

والبدائلُ الثلاثة التي درستها هذه الجولة، بصفوفٍ وصفًا لا بترتيب:

**أ— قائمةُ ذكرَ المستخدم (`recipients: list[str]`، حرفيًّا، بلا خانة عنوان).** صادِقٌ بنيويًّا: `str` لا موضعَ فيه لقرار محلِّل، فلا يمكن أن يحمل طبقةَ حلٍّ. لكنه **غيرُ قابلٍ للوصول** (غ١: إمّا فارغٌ دائمًا وإمّا نسخةٌ من `guests`)، و**غيرُ قابلٍ للقرار** (غ٤: لا مفتاحَ ربط). فهو تمثيلٌ صحيحُ النية، مفقودُ الوسيلة.

**ب— كائنُ مستقبِلٍ منظَّم (`{name, email?, status?, confidence?}`).** هذا هو **الانهيار** الذي تحظره الجولة: `status` و`confidence` ناتجُ محلِّل، وكُتابتُهما في حقل النيّة هي بالضبط «يستبدل الاسترجاعُ نيّةً مختومةً بقيمةٍ مشتقّة» — انتهاكُ شرط (E) في §10.10.4. ولو سقطت صفتا الحلّ وقلّص الحقلُ إلى `{mention, email?}` لبقيت خانةُ `email` دعوةً مفتوحةً لكتابةِ قيمةٍ مشتقّةٍ لاحقًا في موضع نيّة، و`extra="forbid"` وحدها لا تمنع ذلك.

**ج— قائمةُ عناوين مُسنَدة (`recipients: list[EmailStr]` + فحصُ الإسناد).** هي **التصميمُ المقترح**، وهي وحدها التي تجتاز (د): هي القيمةُ الوحيدة التي يستطيع `required_recipients` أن يُبنى عليها بلا جسرٍ مشتقّ. لكنّها **أخطرُ الخيارات إن سقط شرطُ الإسناد**: عندها يصبح النموذجُ مُصرِّحًا بتخمين عنوان، ويصبح العنوانُ القادمُ من الذاكرة داخلَ مشهد الفهم مقبولًا. فالسلامةُ فيها ليست في الشكل بل في الفحص.

**والنتيجةُ الحاسمة**: التصميمُ (ج) **هو** ما يفيّ بالشروط، وهو أيضًا **ما لا يمكن إدخالُه اليوم**، لأن وصولَه يستلزم (غ١) مفردةَ نيّةٍ ثانيةً بحمولتها، و(غ٣) ضبطًا على حدّ الذاكرة، و(هـ) قصدًا في جدول القدرات. وهي تعديلاتُ عقدٍ لا إضافاتُ حقول — وهذا هو سببُ **Design-only**، لا تعذُّرُ التصميم.

#### 10.10.4 التزامُ الإسناد: A–H على التمثيل المقترح

| | الشرط | الحكم | السببُ الميكانيكي |
| --- | --- | --- | --- |
| **A** | أن يَصدر من طبقة الفهم | ✅ | `recipients` حقلٌ في `UnderstandingOutput`، والمُخرِجُ هو `understand_scenario` |
| **B** | أن يمثّل نيّةً لا حلًّا | ✅ *(بشرط الإسناد)* | العنوانُ واردٌ في `<goal>` بحكمٍ حتميّ، فلا يحلّ محلّ الذاكرة ولا محلّ جهات الاتصال |
| **C** | أن يُختم مع دلالات المهمة/العقد | ✅ | `row.scenario` JSONB، يُختم مرةً ولا يُعاد حسابه؛ والاسترجاعُ يعيد التحقّق لا إعادة التوليد |
| **D** | أن يقرّر عليه مُقيِّمُ gmail مباشرةً | ✅ | `required_recipients` يُبنى من العنوان المُسنَد مباشرةً؛ و`args["to"]` هو مفتاح الربط |
| **E** | ألّا يستبدله الاسترجاعُ بقيمةٍ مشتقّة | ✅ | لا كاتبَ ثانيًا للحقل؛ `row.identities` يُكتَب ولا يُنسَخ منه |
| **F** | أن يبقى حلُّ جهات الاتصال/المزوّد خلفَ النية | ✅ | `CONTACT_MATCH` يبقى شرطًا على الإرسال؛ والمطابقةُ تُثبتُ وجودَ العنوان لا إمدادَه |
| **G** | ألّا تكون الذاكرةُ مصدرَ نيّة | ✅ *(بالفحص، لا بغيره)* | العنوانُ المُسنَد لا يَرِد في `<preferences>`، فلا يمكن لذكرى أن تُرضي فحصَ الإسناد — **واليوم بلا فحصٍ أصلًا** (غ٣) |
| **H** | ألّا يُفتَح مسارُ ترخيصٍ ثانٍ | ✅ | `LIVE_SEALABLE_PROFILES` مفردةٌ مغلقة، وفحصُ `create_task` العنصرُ الوحيد فيها؛ والترخيصُ تعديلٌ صريح في موضعٍ واحد |

**والنتيجةُ أن الشروط الثمانية تصمد — وثمّ لا يُنفَّذ شيء.** فبين (A) و(H) شرطان لا يقرّران شيئًا في حدّ ذاتهما بل يفرضان تعديلَ عقد: **(د)** يفرض مفردةَ نيّةٍ ثانيةً وجدولَ قدراتِ gmail، و**(ب)/(ج)** تفرض ختمَ محتوى الرسالة (انظر أدناه). وهذه الثلاثة خارجٌ عن «الإضافة الدنيا» التي تسمح بها الجولة، فالتنفيذُ الآن كان سيضيف تمثيلًا **غيرَ قابلٍ للوصول** — وهو أسوأُ من تأجيله، لأن حقلًا لا يملؤه شيءٍ لا يثبت شيئًا بل يُوهم بأنّه يثبت.

**وقيدٌ إضافيٌّ يقيّده التصميمُ نفسُه، لم يُسمَّه في جولاتٍ سابقة**: `GmailSendArgs` تتطلّب `to` و`subject` و`body`، و`GmailSendCriteria` ترفض `subject` و`body` **لسببٍ مذكور**: لا مصدرَ مختومًا لهما. فنيّةُ المستقبِل وحدها **شرطٌ لازمٌ لا كافٍ**؛ فنيّةٌ مختومةٌ كاملةٌ لرسالةٍ تقتضي أيضًا ختمَ الموضوع والمتن نيّةً، وإلا صارت رسالةٌ اختُرع محتواها وقت التنفيذ قابلةً للتصريح بأنها فُيّلت. وهذا وحده يستبعد ترخيصَ المجال حتى لو أُنجز التمثيلُ مثاليًّا. (وهذا هو موضعُ التقاطع الذي رصدته الجولة: §10.10.3 يذكره، والاختبار `test_recipient_intent_alone_would_leave_the_domain_half_sealed` يثبّته.)

| **DEFERRED** | مفردةُ نيّةٍ ثانية (`send_message`) بحمولتها · فحصُ الإسناد في `understand_scenario` · ختمُ الموضوع والمتن نيّةً · جدولُ قدرات gmail · قيادةُ gmail حيًّا · cardinality `required_recipients` مقابل `to` المفرد |
| **LICENSE** | `gmail_send` **لا يزال غيرَ مرخَّصٍ للتسجيل الحي**، لأن شرطَ (د) لم يتحقَّق: لا تمثيلَ له في المستودع بعد |

**وما كان مفتوحًا بعد الجولة الثانية**: هل يحتاج مجالُ gmail إلى مفردة نيّةٍ ثانيةٍ كاملة، أم يكفي توسيعُ `intent` ليحتمل شكلين مختلفين تحت حقلٍ واحد. وقد جاء الجوابُ في §10.10.6–§10.10.12: **مفردةٌ ثانيةٌ كاملة** هي المرشَّحةُ الوحيدةُ التي تحفظ النيّةَ في الموضعِ الوحيدِ الذي يُعاد التحقّقُ منه — لكنّها تحتاج ثلاثةَ قراراتٍ لا يمكن استنتاجُها من تحليلِ المسار.

#### 10.10.6 الجولةُ الثالثة: العقدُ الكامل — والخاتمةُ أنّ حدَّ الختمِ يسبق القيمةَ التي كان سيُبقيه

سألت هذه الجولة ما تركته الجولتان السابقتان مفتوحًا: ليس «أيُّ تمثيلٍ يحفظ المستقبِل» — فذاك محسومٌ في §10.10.3 — بل **ما العقدُ الدلاليُّ الأدنى الذي يجعل طلبَ إرسالِ رسالةٍ قابلًا للختمِ المشروع**، وأين يقف الحدُّ بين نيّةِ المستخدم والإسنادِ الحتميّ وبياناتِ التنفيذ.

والجوابُ الذي خرجت به الجولةُ ليس قائمةَ حقول، بل **ترتيبًا زمنيًّا**. وهذه هي النتيجةُ المركزية:

> **الرخصةُ تُمنحُ قبل أن توجد القيمةُ التي كان يمكن وزنُها.**

المسارُ الفعليُّ في المستودع:

```text
runtime_submit                              (api/runtime.py)
  └─ build_slice_contract(goal)             لا يَرد scenario في توقيعه إطلاقًا
  └─ create_task(contract)                  يُختم fulfillment_profile على الصفّ
  └─ RuntimeExecution(scenario=None, identities=[])

runtime_trigger                             (runtime/service.py::_drive)
  └─ Stage 1   understand_scenario(...)     يُختم scenario  (JSONB، يُعاد التحقّقُ منه)
  └─ Stage 2   _resolve_guest_identities   يُملأ identities (JSONB، بلا مخطّط)
  └─ …        التنفيذ
  └─ VERIFYING _fulfillment_outcome         Criteria تُبنى هنا من الصفّ
```

`build_slice_contract` يقرأ `goal` وحده، و`SLICE_FULFILLMENT_PROFILE` ثابتٌ `calendar_meeting` لكل مهمةٍ يولّدها الـslice؛ و`create_task` هو المُسجِّلُ الوحيدُ لـ`Task.fulfillment_profile`، وهو الذي يرفض ما ليس في `LIVE_SEALABLE_PROFILES`. فليس في دورة الحياة **أيّ لحظةٍ تقف فيها قيمةُ مستقبِلٍ موجودةً ويَزنها المستودعُ قبل أن يمنحَ إذنَ الختم**. وهذه خاصيةٌ زمنيةٌ لا يزيلها تغييرُ مخطّط: فإضافةُ حقلٍ لا تُنشئُ اللحظةَ المفقودة، بل تُضيفُ قيمةً في موضعٍ لا تقرأه البوّابة.

ولهذا يبقى ما حدّدته الجولتان السابقتان — عنوانٌ مُسنَدٌ إلى Goal، وختمُ الموضوع والمتن — **شرطًا لازمًا لا كافيًا**، حتى لو استوفى كلٌّ منهما شرطَه على حدة.

#### 10.10.8 الموضوعُ والمتن: لا مصدرَ لهما، ولا بانيَ لهما، والمتنُ غيرُ مشهود

الجولةُ السابقة قالت: «لا مصدرَ مختومًا للموضوع ولا للمتن». وهذه الجولةُ تضيف ثلاثَ حقائقَ تجعل المسألة أصعبَ من نقصِ حقل:

1. **لا مسارَ لتمرير المحتوى أصلًا.** `PlanStep` حقوله `{step_id, order, action, purpose, inputs, expected_output, verification_hint}` وليس فيها `arguments`؛ و`inputs` نوعُه `list[str]` يُنسَخُ إلى عقدة الـIR ولا يُقرأُ كحقولِ استدعاءٍ أبدًا. فالمسؤولُ الوحيدُ عن وسائطِ الأدوات هو `_intents_for`، وهو تعدادٌ مغلقٌ لأربعِ قدراتٍ تقويمية، و`capability_to_tool` يُعيد `None` لما ليس فيها فيرفع `RuntimeFatal`. **أيُّ إرسالٍ مُقادٌ اليوم كان مُلزَمًا ببناءِ موضوعٍ ومتنٍ من مخطّطٍ لا يحمِّلهما** — أي من ثابتين، تمامًا كما يرجع `MeetingWindow.title` إلى قيمته الافتراضية `"KAI meeting"`.
2. **الموضوعُ يُقارَنُ بالطلب لا بالنيّة.** `verify_send` يقارن `message_id` و`thread_id` و`SENT` والمُرسِلَ والمستقبِلَ **والموضوع** — كلُّها مقابل `req`، أي مقابل ما أرسلناه. فـ`verified=True` تعني «ردّ المزوّدُ طلبَنا»، وهي دعوى عن الطلب لا عن النيّة.
3. **المتنُ لا يُقارَنُ قط.** `verify_send` لا يقرأ `body` ولا `body_text` أصلًا: قراءةُ المزوّدِ بنصٍّ مختلفٍ تمامًا — أو فارغٍ — تُرجعُ صفرَ أوجهِ اختلاف. فحتى لو وُجِد متنٌ مختومٌ لَما كان له دليلٌ يقرؤه مُقيِّم.

**الأثرُ على التصميم**: سلطةُ الموضوع والمتن ليستا مسألةَ حقل، بل **قرارَ سياسة**: هل يُشتقُّ الموضوعُ منGoal للمستخدم؟ ومن أيّ صلاحيةٍ؟ وما الذي يجعل نصًّا ولَّده النموذجُ نيّةً لم يُكتبها المستخدم؟ المستودعُ لا يجيب عن واحدٍ من هذه الأسئلة، والمجالاتُ الثلاثةُ (`subject` و`body` و حدُّ الختم) هي ما يُبقي البوّابةَ مغلقة.

#### 10.10.9 الإسناد: ما يستطيع المحلِّلُ أن يقوله، وما لا يستطيع

سُئل عن المفردات `VALID` و`AMBIGUOUS` و`UNRESOLVED` و`INVALID`. والجوابُ من `kai/identity/service.py`:

| الحالة | ما يعنيه في المستودع | مُقابلٌ مقصود |
| --- | --- | --- |
| `CONTACT_MATCH` | مطابقةٌ تامّةٌ واحدةٌ لبريدٍ أو هاتفٍ على حسابٍ واحد | `VALID` |
| `PROVIDER_VERIFIED` / `CHANNEL_VERIFIED` | العنوانُ هو **بريدُ الحساب** | **غيرُ قابلٍ للوصول**: الـruntime لا يُمرِّر `provider` ولا `channel` قط |
| `CONFLICTING` | جهتان متمايزتان، أو مرشِّحانِ واسعانِ بلا مُعرِّفٍ تامّ | `INVALID` |
| `UNKNOWN` | لا مطابقةً تامّةً واحدة… **أو اثنتان على جهةٍ واحدة** | يجمعُ `UNRESOLVED` و`AMBIGUOUS` معًا |

وثلاثُ نتائجٍ ثابتةٍ بالاختبار:

* **لا وجودَ لـ`AMBIGUOUS`.** مفرداتُ `IdentityStatus` خمسٌ، فيها `CONFLICTING` و`UNKNOWN` ولا ثالثَ بينهما. وجهٌ واحدٌ طابق بالبريدِ **و**الهاتف معًا يُنتجادعوىين تامّتين، فيسقط شرطُ `len(exact_claims) == 1`، ويهبط إلى `UNKNOWN` — وهي حالةٌ بريئةُ ظاهرُها غامض. فالتمييزُ الذي يحتاجه العقدُ بين «وجدتُ واحدًا» و«وجدتُ اثنين لجهةٍ واحدة» و«لم أجد شيئًا» **لا مَثَلَ له فيStatus**، وهذا بعينه مانعٌ من صياغة قاعدةِ إسنادٍ نظيفة.
* **الاسمُ لا يُسقِط أبدًا.** `_exact_claims` يقرأ `query.email` و`query.phone` ولا يقرأ `query.name` قط؛ فمطابقةُ الاسمِ إن وجدت تُنتج `CONFLICTING` أو تُبقي `UNKNOWN`. **ولهذا يصحّ ما انتهت إليه الجولةُ السابقة**: لولا أن يُكتب العنوانُ في Goal لَما وُجدَ إليه مسارٌ حتميٌّ أصلًا.
* **`email` يبقى معبَّأً عند عدم اليقين.** في حالة «طابقَ مرّتين» يعيد `IdentityResolver` الحالةَ `UNKNOWN` ** ومع ذلك يبقى `resolved.email` عنوانًا كاملًا**. فقراءةُ `email` وحدها ليست قراءةً آمنة، ولهذاحرسُ الـruntime على `status` عند الكتابة لا على العنوان.

#### 10.10.10 الاستدعاء: التلقيمُ لا إعادةُ الحساب

النموذجُ المتوقَّعُ في هذه الجولة كان: «النيّةُ تبقى وإعادةُ وإعادةُ الإسنادِ لا تصير نيّةً جديدة». وفحصُ المستودع يُظهر أن هذا ينطبق **بالقوة، لكنّه فارغ**:

```text
if not row.identities:                 # runtime/service.py::_drive
    identities = await self._resolve_guest_identities(...)
    row.identities = identities
```

الحارسُ يمنع إعادةَ السؤال، فلا يُعاد إسنادٌ أبدًا؛ فمَن يُعيد اشتقاقَ «نيّةٍ» من إسنادٍ جديدٍ لا وجودَ له اليوم. وثمنُ ذلك أنّ جهةَ اتصالٍ تغيَّرت بعد التنفيذِ الأصلي **غيرُ مرئيةٍ للاستدعاء**، ولا أثرَ يُسجّل أنّها استُشيرت ثانية.

والخطرُ الحقيقيُّ ليس إعادةَ الحساب، بل **استمرارَ التلقيم بلا مخطّط**. فالعمودان كلاهما `JSONB`، لكن `scenario` يُعاد التحقّقُ منه بـ`UnderstandingOutput` في كلِّ مُشغِّل، بينما `identities` يُقرأ `list(row.identities)` بلا نموذجٍ واحد. و`gmail_send_criteria` تقرأ `item["email"]` ولا تقرأ `status`، والحرسُ الوحيدُ على الحالة السليمة يقع **عند الكتابة فقط**. فصفٌّ سجَّل `CONFLICTING` — أي فشِلَ الإسناد — يبقى بعد الاستدعاءِ يولّدُ `required_recipients`، وتُعتَبَرُ رسالةٌ إلى ذلك العنوانِ `FULFILLED`.

هذه هي صيغةُ «الاستمرارُ لا يخلقُ سلطة» ملموسةً: هنا لا يكفُ عنخلقِ السلطة، بل **يهدمَ السجلَّ بأنّ الإسنادَ لم يتحقَّق**.

#### 10.10.11 التصاميمُ الثلاثةُ المرشَّحة (بلا ترتيب)

**(أ) مسرودُ نيّةٍ مُرسلٍ (Sealed Message Intent).** مشهدٌ ثانٍ بـ`intent = "send_message"` يحمل `{recipients, subject, body}`، يُختم في `scenario` كما يُختم الـwindow اليوم. صاحبه: طبقةُ الفهم. نقطةُ الختم: نفسُ نقطة الـscenario. نقطةُ الإسناد: بعد الختم، خارجَه. سلطةُ الموضوع والمتن: النصُّ الختومُ نفسُه، فلا مشتقَّ ولا مولَّدًا. إسقاطُ المُقيِّم: `required_recipients` و`subject` من القيمتَين الختومتَين؛ و`body` لا يُقارَن، فيبقى بلا دليل. الاستدعاء: `scenario` يُعاد التحقّقُ منه، فالقيمُ محفوظة. الأثر: توسيعُ المفردة، وجدولُ قدراتٍ جديد، وختمُ `body` بلا شهادة. مخاطرة: **الحدُّ يبقى حيث هو** — الرخصةُ تُمنحُ في التسليم وقبل الختم.

**(ب) ختمُ الإرسال في العقد بدلَ المشهد.** فهرسُ recipients في `TaskContractInput` يُختم عند `create_task`. صاحبه: طبقةُ العقد. الأثر: يُعيد مشكلةَ الجولةِ الأولى — وهو أنّ نيّةً تُستنتج من goalٍ حرٍّ قبل أن يُفهم — ويجعل الختمَ مسنودًا ببوّابةٍ تقع **قبل** الفهم لا بعده. رفضُه مُوثَّقٌ لأنّ `build_slice_contract` اليوم لا يقرأ الـscenario أصلًا، فإضافةُ recipients إليه تعني تغذيةَ العقد بناتجِ الفهم، والحسمُ يتطلّب خطوةَ فهمٍ لا حقلَ contractٍ جديدًا.

**(ج) content-as-contract: ختمُ الرسالة كمعيارٍ مستقلّ.** يُختم المتنُ وحده في `SuccessCriteria` ويُحمل `_message_digest`. صاحبه: طبقةُ الإنجاز. الأثر: يجعلُ الحقلَ *معيارًا* لا نيّةً — أي يُقرّر عليه بمجرّد وجوده لا بعلاقته بالنيّة — فينقلب على البند (E)، ويضيف شرطًا لا دليلَ له اليوم لأنّ `verify_send` لا يقرأ المتن. وليس في المستودع ما يقابلها.

**ما يبرّره المستودعُ فعلًا:** (أ) وحدها هي التي تحفظ النيّةَ في الموضعِ الوحيد الذي يُعاد التحقّقُ منه. لكنّها تحتاج قرارًا في **سلطة الموضوع والمتن**، وقرارًا في **موضع حدِّ الختم**، وقرارًا في **مطابقة cardinality** — وثلاثتُها خارجُ ما يسمح به «أدنى تغيير».

#### 10.10.12 بوّابةُ القرار: Design-only

شروطُ الانتقال إلى التنفيذ **ثمانية**: أربعةٌ منها محسومةٌ بالمستودع وأربعةٌ غيرُ محسومة — وعددُ صفوفِ الجدول أدناه ثمانيةٌ بالضبط، لا سابعَ في القائمة.

| الشرط | الحالة | الشاهد |
| --- | --- | --- |
| تمثيلُ نيّةِ المستقبِل | **محسوم** | عنوانٌ يَرِد حرفيًّا في `<goal>`؛ وهو المفتاحُ الوحيدُ الممكن (§10.10.3) |
| سلوكُ الاستدعاء | **محسوم** | التلقيمُ لا إعادةُ الحساب؛ و`scenario` يُعاد التحقّقُ منه |
| إسقاطُ الإنجاز | **محسوم** | `required_recipients ⊆ {args["to"]}`، مع تناقض cardinalityٍ قائم (§10.10.7) |
| عددُ المفردة | **محسوم** | `gmail.send` غيرُ مضافٍ إلى `SLICE_ALLOWED_TOOLS` ولا `CAPABILITY_TO_TOOL` ولا `_intents_for` |
| **قاعدةُ الإسناد** | **غير محسومة** | لا `AMBIGUOUS` في `IdentityStatus`؛ و«طابقَ مرّتين» يهبط إلى `UNKNOWN` مع بقاء العنوان (§10.10.9) |
| **سلطةُ الموضوع** | **غير محسومة** | لا مصدرَ ولا باني؛ والمزوّدُ يقارنُه بالطلب لا بالنيّة |
| **سلطةُ المتن** | **غير محسومة** | لا مصدرَ ولا باني؛ **والمزوّدُ لا يقارنُه أصلًا** فلا دليلَ للمعيار |
| **حدُّ الختم** | **غير محسوم** | الرخصةُ عند التسليم، والقيمةُ بعد الفهم والإسناد؛ وهي ترتيبٌ لا مخطّط |

**الحكم: Design-only.** أربعةُ شروطٍ من ثمانيةٍ لا يملؤها حقل، والبوّابةُ مغلقةٌ لذلك لا لأجلِ نقصِ محلِّل.

`gmail_send` **يبقى غيرَ مرخَّصٍ للتسجيل الحي**، و`LIVE_SEALABLE_PROFILES` تبقى `{calendar_meeting}`، ومسارُ الختمِ الحيّ يبقى واحدًا. والخطوةُ التالية ليست حقلًا، بل ثلاثةُ قرارات: **مَن يحقُّ له أن يؤلِّف نصًّا يُرسل باسم المستخدم**، و**أين يقف حدُّ الختم**، و**كيف يُميَّز الإسنادُ الغامضُ عن غيرِه**. وما دامت مفتوحةً، فالعنوانُ المُسنَدُ وحده لا يكفي، ونيّةُ الموضوع والمتن وحدَ الختم هي مواضعُ النقصِ الحقيقيّة.

### 10.11 الجولةُ الرابعة: ثلاثةُ أسئلةٍ في أعلى المسرح (Upstream Authority Review v1)

الجولاتُ الثلاثُ السابقة نزلت من_ICVE«الاختيار: من يملأ `body`» إلى «الترتيب: أين يقف الختم». وهذه الجولةُ تصعدُ إلى مستوى سؤالٍ أعلى منها، وهو السؤالُ الذي يجعل الثلاثةَ السابقةَ أسئلةً فرعية:

1. **من يحقُّ له أن يؤلِّف قيمةً يرسلها KAI باسم المستخدم؟** لكلِّ حقلٍ على حدة.
2. **أين يقف حدُّ الختم بالضبط؟** وما الشيءُ الذي يَحملُ السلطةَ حين يُختم؟
3. **ماذا يحدث حين يفشل الإسنادُ أو يغموض بعد ذلك؟** وهل يستطيع الاستدعاءُ إعادةَ إنتاج السلطة نفسها بلا إعادةِ تأليف؟

والجوابُ الذي خرجت به الجولةُ ليس أطولَ من جوابِ سابقاتها، بل **أضيقَ وأصرحَ**:سؤالٌ واحدٌٌ من الثلاثة **مكتوبٌ في الشيفرة اليوم**، واثنان **غيرُ مكتوبين في أيّ موضع**، والرابعُ —الإسنادُ— كان في الجولةِ الثالثة «يحتاج `AMBIGUOUS`»، و**هذا خطأٌ أثبتَه الفحصُ الآن**.

#### 10.11.1 التفكيك: خمسةُ أسئلةٍ تحت ثلاثة

قبل الحكم، تفكيكُ السؤالِ الأول إلى قيمَه الفعلية. والجدولُ يقرأ من الشيفرة لا من التخمين:

| القيمة | من أين تأتي | صاحبُ التأليف | حقلُ أداةٍ؟ | في ملخّصِ الموافقة؟ | داخلُ التجزئة؟ |
| --- | --- | --- | --- | --- | --- |
| `POST /gmail/send` → `to` | جسمُ طلبِ HTTP | **المستخدم** (حرفيّ) | `SendBody.to` | لا مسارَ بوّابة | **لا** — لا مهمّةَ أصلًا |
| `POST /gmail/send` → `subject` | جسمُ طلبِ HTTP | **المستخدم** (حرفيّ) | `SendBody.subject` | لا مسارَ بوّابة | **لا** |
| `POST /gmail/send` → `body` | جسمُ طلبِ HTTP | **المستخدم** (حرفيّ) | `SendBody.body` | لا مسارَ بوّابة | **لا** |
| `gmail.send` → `to` | **لا بانيَ له** | — | `GmailSendArgs.to` | **نعم** | نعم |
| `gmail.send` → `subject` | **لا بانيَ له** | — | `GmailSendArgs.subject` | **نعم** | نعم |
| `gmail.send` → `body` | **لا بانيَ له** | — | `GmailSendArgs.body` | **لا** | نعم |
| المُرسِل `from` | `GoogleAccount.email` | **المزوّد** (مصافحةُ OAuth) | **غيرُ موجودٍ أصلًا** | لا | لا |
| `scenario.intent` | نموذجُ الفهم | **النموذج** | — | لا | نعم |
| `scenario.window.title` | نموذجُ الفهم | **النموذج** | `title` | **نعم** | نعم |
| `identities[*].email` | `IdentityResolver` | **محلِّلٌ حتمي** | `attendees` | **نعم** | نعم |
| `evidence["message_id"]` | المزوّد | **المزوّد** | — | لا | نعم |
| مطابقةُ `to`/`subject` في `verify_send` | المزوّد مقابل **الطلب** | تحقّقٌ تنفيذي | — | لا | نعم |

ثلاثُ حقائقَ تقرأ من الجدول كاملًا:

* **`GmailSendArgs` ليس فيه حقلُ مُرسِل.** فحصُ الحقول: `['body', 'subject', 'to']` والمطلوبُ منها الثلاثة. فالمُرسِلُ لا يؤلِّفه أحدٌ من داخل KAI؛ `api/gmail.py:8` يصرّح بذلك حرفيًّا: «the sender is taken from the stored account, never from the request». **المُرسِلُ إذن متروكٌ لسلطةِ المزوّد بالمصافحة، وهذا هو الجوابُ الوحيدُ الآمنُ له.**
* **`title` precedentٌ قائمٌ وكامل.** عنوانٌ لمْ يكتبه المستخدمُ يمرّ: نموذجًا → ختمًا في `scenario` → مدخلَ تنفيذٍ عند المزوّد → ويظهرُ في ملخّصِ الموافقة. فالكودُ **يقبل** نصًّا مولَّدًا يصلُ إلى المزوّد متى كان **مرئيًا للموافِق**. وهذا هو الحدُّ الفاصلُ الحقيقيُّ في الجولة، لا سؤالُ «هل يُسمحُ للنموذجِ أن يتكلّم».
* **الرؤوسُ الثلاثةُ في مسارٍ واحد، ومجالاتُه الثلاثةُ في مسارٍ آخر.** لا يلتقيان.

#### 10.11.2 نتيجةُ الفحص: السلسلةُ مُغلقة، فلا مسارَ حيَّ إلّا حروفُ المستخدم

`send_and_verify` له **موضعان** في المستودع لا ثالثَ لهما:

```text
api/gmail.py:195              ← من المستدعي مباشرةً، بلا بوّابة
tools/adapters/gmail.py:159   ← عبر ToolGateway
```

الموضعُ الأوّل يستدعي `kai.gmail.service.send_and_verify` مباشرةً. لا `ToolGateway`، ولا `PolicyEngine`، ولا `ApprovalService`، ولا `Task`، ولا `RuntimeExecution`، ولا `evidence`، ولا `gmail_send_criteria`. تفويضُ الحسابِ عبر `_resolve_account(session, current, account_id)` بمفتاح `(current.tenant_id, current.user_id)` وحده.

والموضعُ الثاني **موجودٌ في الشيفرة ولا يبلغه شيء**. والدليلُ سلسلةٌ مغلقةٌ كلُّ حلقةٍ منها مقيسة:

1. `tasks/service.py:111` — `create_task` **يرفض** أيَّ عقدٍ لا ينتمي إلى `LIVE_SEALABLE_PROFILES = {calendar_meeting}` بـ`UnlicensedFulfillmentError`. فهو **الكتابةُ الوحيدةُ التي تمنح** قيمةَ `Task.fulfillment_profile` من خارج.
2. فأيُّ صفٍّ صادرٌ من `create_task` لا يحمل `gmail_send` **إطلاقًا**، فلا يبقى في القاعدة ما يدعو الفرعَ الثاني (س 1547).
3. `runtime/service.py:1530` — `_fulfillment_outcome` يقرأ `profile = task.fulfillment_profile` ويشتقُّ منه فقط، و`_intents_for` (س 769) تُستدعى بنفس القيمة.
4. فلا يُنتَج نيّةُ `gmail.send` البتّة، فلا تصل إلى `ToolGateway`، فلا يُبلَغُ المحوِّلُ في `tools/adapters/gmail.py`.
5. والطريقُ الحيُّ الوحيدُ المتبقّي هو `POST /gmail/send` بحروفِ المستخدم.

ويؤكّده الشيفرةُ نفسُها تعليقًا: «**``gmail_send`` is the second branch, and it is not reachable from the live slice**» (س 1502)، و«``gmail_send`` stays in the vocabulary but is not listed, so it remains sealable at the schema layer and is **refused here**» (`tasks/service.py:71`).

**فالجوابُ الميكانيكيُّ للسؤالِ الأول مكتوبٌ في الشيفرة اليوم**: القيمُ الثلاثُ التي يرسلها KAI فعليًّا **حرفيّةٌ من المستخدم**، ولا نموذجَ في المسارِ قطعًا. **ومسارُ الـruntimeِ لا يملك فرعًا حيًّا لـgmail أصلًا** — لا بانيَ لـ`subject` ولا `body` ولا `to`، لأن `_intents_for` تعدادٌ مغلقٌ وقدراتُه تقويمية.

> **وتنبيهٌ على دقّةِ الوصف:** ليس أدقَّ أن يُقال «للإرسال موضعٌ واحدٌ في المستودع». الموضعان اثنان؛ الأدقُّ أنّ **موضعًا واحدًا يبلغه مستخدمٌ حيّ**. وهذا فرقٌ مهمٌّ потому أنّه يصف **البلوغَ لا الكتابة**: الموضعُ الثاني كودٌ صحيحٌ ومختبَرٌ ومُوصَلٌ، وحذفُه أو إبقاءُه قرارٌ منفصل.

وهذا يقلب صياغةَ الجولةِ الثالثة. لم يكن السؤالُ «من يملأ الحقل؟» بل **«أيُّ مساراتٍ يرسل فيها KAI فعليًّا؟»** — والجوابُ: واحدٌ حيّ، وهو خارجَ مسرحِ الـruntime، ومكتوبٌ بالكاملٍ بحروفِ المستخدم. فسؤالُ التأليفِ لا يظهرُ إلا عند إضافةِ فرعِ gmail، وهو بالضبط ما لا تفعله هذه الجولة.

#### 10.11.3 عدمُ التماثل: المتنُ مربوطٌ بالمفتاحِ ومخفيٌّ عن الموافِق

هذه أقوىُ نتيجةٍ ميكانيكيةٍ في الجولة، وهي ثلاثةُ أسطرٍ مُقاسة:

```text
_summary_arg_fields   = ('to', 'subject', 'title', 'date', 'start_time', 'end_time',
                        'timezone', 'attendees', 'query', 'recipient')
_sensitive_arg_fields = frozenset({'body', 'body_html', 'content', 'message'})
```

وملخّصُ الموافقةِ الفعليُّ المُقاسُ لأمرِ gmail:

```text
Send an email from the user's account and verify, via read-after-send, that the
provider accepted the message
to: pat@example.com
subject: Status
```

**لا أثرَ للمتن.** لكنّ `canonical_payload` يبني `arguments` من `_canonical_value(dict(arguments))` على **كلِّ الوسائط بعد التحقّق**، فلا يسقطُ منها شيء. والمقاسُ يؤكّد أنّ البصمةَ تتغيّر بتغيّر المتن بتغييرِ مسافةٍ واحدة، وتتغيّر بتغيّر الحساب.

فالنتيجةُ مقلوبةٌ عن السحر المعتاد — **الربطُ صحيحٌ والإخفاءُ هو الخلل**:

| الخاصّية | `to` | `subject` | `body` |
| --- | --- | --- | --- |
| داخلُ البصمة | نعم | نعم | **نعم** |
| يظهرُ للموافِق | نعم | نعم | **لا** |
| تعديلُه يُبطلُ الموافقةَ السابقة | نعم | نعم | **نعم** |

أي أنّ **الموافقةَ مربوطةٌ بخوارزميةِ تجزئةٍ بنصٍّ لم يرَه صاحبُ القرار**. وهذا ليس «رقابةً ضعيفة»، بل هو **نقصُ موافقةٍ مُطّلعة**: مَن يضغط `APPROVE` يوافق على شيءٍ لا يستطيع قراءته. و`_SENSITIVE_ARG_FIELDS` — وهو المُثبِتُ الوحيدُ لنيّةِ «لا تُسرَّب المتنات» — **مُعلَنٌ ولا يُستعمَل**: البحثُ في `src/kai` يجمعُ تعريفَه وحدَه، بلا مرجعٍ واحد. فالنّيّةُ موثّقةٌ في اسمِ ثابتٍ ميّت، لا في سلوك.

والتناظرُ مع `title` صار حاسمًا: العنوانُ المولَّدُ يمرُّ لأنه **مرئيّ**؛ والمتنُ المولَّدُ لا يمرُّ، وهو ما كان ستُغلقَ به البوّابةُ في أيّ تصوُّرٍ يُدخلُ نموذجًا على المتن.

#### 10.11.4 الإسنادُ: الخللُ في المُسند لا في المفردة — وهذا تصحيحٌ صريحٌ للجولة الثالثة

كتبت الجولةُ الثالثة (§10.10.9، §10.10.13): «قاعدةُ الإسناد (تحتاج `AMBIGUOUS`)». **والفحصُ الآليُّ ينفي هذا**، فيجعلُ البندَ قابلًا للحسم:

```text
identity/service.py:175   elif len(exact_claims) == 1:  status = CONTACT_MATCH
identity/service.py:247   distinct_ids = {claim.contact.resource_name for claim in exact_claims}
identity/service.py:309   C1: if len({claim.contact.resource_name for claim in exact_claims}) > 1: return True
```

السطرُ 175 يعدُّ **الدعاوى**؛ والسطران 247 و309 يعدّان **الكيانات المتمايزة**. المعياران لا يتّفقان، والفرقُ يقعُ على الحالةِ الأكثرِ ثقةً في النظام. الحالاتُ الثمانيُ المُقاسة:

| # | المُدخل | `claims` | `distinct` | الحالةُ اليوم | العنوان | الثقة |
| --- | --- | --- | --- | --- | --- | --- |
| A | لا مُعرِّفَ أصلًا | 0 | 0 | `UNKNOWN` | `None` | 0.0 |
| B | مُعرِّفٌ تامّ واحد، جهةٌ واحدة | 1 | 1 | `CONTACT_MATCH` | ✔ | 0.5 |
| C | **مُعرِّفان تامّان، جهةٌ واحدة** | **2** | **1** | **`UNKNOWN`** | **✔** | **0.0** |
| D | مُعرِّفٌ تامّ واحد، جهتان متمايزتان | 2 | 2 | `CONFLICTING` | ✔ | 0.0 |
| E | بريدٌ لجهةٍ والهاتفُ لغيرها | 2 | 2 | `CONFLICTING` | ✔ | 0.0 |
| F | اسمٌ فقط، مرشِّحانِ واسعان | 0 | 0 | `CONFLICTING` | `None` | 0.0 |
| G | اسمٌ فقط، مرشِّحٌ واحد | 0 | 0 | `UNKNOWN` | `None` | 0.0 |
| H | مُعرِّفٌ تامّ، لا مطابقة | 0 | 0 | `UNKNOWN` | `None` | 0.0 |

**الحالةُ C هي قلبُ الخلل**: جهةٌ واحدةٌ طابقت بالبريدِ **و**الهاتف معًا — أي أقوى دليلٍ متاح، إذ يضيف `derive_confidence` نفسه زيادةً عند تعدُّد المصادر (`len({source}) >= 2`) — تهبط إلى `UNKNOWN` بثقةِ صفر. **التوثيقُ يقلّلُ الثقة.** والإصلاحُ سطرٌ واحد: `len(distinct_ids) == 1` بدل `len(exact_claims) == 1`، و`distinct_ids` محسوبةٌ أصلًا في السطر 247 لاشتقاق `contact_id`.

**والأهمّ: المفردةُ لا تحتاج أن تكبر.** `CONFLICTING` عبر C1 **تعني اليومَ أصلًا** «أكثرُ من كيانٍ تامّ التمييز» — أي أنّ التمييزَ بين الغموض والغياب **موجودٌ بالفعل** داخلَ المفردة، ومُطبَّقٌ في `_has_conflict` قبل أن يُقرَّر شيء. والحالاتُ F وA وH تُميَّز trioً كاملًا بلا عضوٍ جديد.

والأقوى من ذلك كلِّه أنّ العلاقةَ بين المفردتين **مكتوبةٌ في الشيفرة**، لا مستنتجة: `tools/gateway.py:571` يُعرِّف `_IDENTITY_TO_POLICY` خريطةً تامّةً **خمسة←ثلاثة**، والبوّابةُ تشترطها باشتراكٍ بلا بديلٍ افتراضي (س 369: `return _IDENTITY_TO_POLICY[result.status]`):

```text
CONTACT_MATCH       -> VERIFIED  ┐
CHANNEL_VERIFIED    -> VERIFIED  ├ ثلاثةٌ إلى واحد
PROVIDER_VERIFIED   -> VERIFIED  ┘
UNKNOWN             -> UNKNOWN
CONFLICTING         -> CONFLICTING
```

وثلاثُ نتائجٍ في الطرف الآخر لا أكثر: `rule_identity` (تسلسلها قبل `risk_approval`، فلا يجرّ تفويضٌ خطأً على رفض) تُعطي تحقّقًا لـ`VERIFIED`، وتصعيدًا لـ`UNKNOWN`، ورفضًا لـ`CONFLICTING`، وتُمسكُ لسانها تحت `MEDIUM`. فالخريطةُ **تامّةٌ على المخارج**: لا حالةَ رابعةَ يمكن أن تحمل معنًى رابعًا. ولو أُضيف عضوٌ جديدٌ لكان إمّا تكرارًا لـ`UNKNOWN` أو لـ`CONFLICTING`، أو — إن وُضع في `VERIFIED` — تنويعةً جديدةً للإيجاب لا للإسناد. **الجمعُ بين غيابٍ ودلالةٍ حتميّةٍ في مفردةٍ واحدةٍ سبعةَ أعضاءٍ بلا فائدةٍ ظاهرة.

فـ`AMBIGUOUS` لو أُضيفَ لكان **تكرارًا** لا تمييزًا. وهذا يصحّحُ قائمتَي `DEFERRED` في §10.10.13.

#### 10.11.5 الخللُ الثاني في الإسناد: الكاتبُ صارمٌ والقارئُ لا

المقاسُ الثاني يكشفُ عدمَ تماثلٍ بين موضعَي الاستعمال، ولولاه لَما كان خللًا حيًّا اليوم:

* **الكاتبُ صارم.** `runtime/service.py:686` يرفع `RuntimeFatal` عند `resolved.status not in _POSITIVE_IDENTITY`، والسطرُ 526 يلتقطُه ويعودُ بـ`_fail` **قبل** السطر 527 `row.identities = identities`. فصفٌّ يحمل `UNKNOWN` أو `CONFLICTING` **لا يُكتبُ أصلًا** على المسارِ الحيّ.
* **القارئُ غيرُ صارم.** `gmail_send_criteria` (`runtime/fulfillment.py:454`) و`calendar_meeting_criteria` (`runtime/fulfillment.py:414`) يبنيان المجموعةَ بـ`item["email"]` **ولا يقرآن `status` قط**. والمقاس:

  | `status` في الصفّ | `required_recipients` | `required_attendees` |
  | --- | --- | --- |
  | `CONTACT_MATCH` | `{ann@…}` | `{ann@…}` |
  | `UNKNOWN` | `{ann@…}` | `{ann@…}` |
  | `CONFLICTING` | `{ann@…}` | `{ann@…}` |
  | **لا `status` أصلًا** | `{ann@…}` | `{ann@…}` |

**فالعيبُ في القارئ وحده، وهو today غيرُ قابلٍ للاستغلال على المنتجِ الحيّ الوحيد**، لأنّ الكاتبَ لا يترك له صفًّا فاسدًا. وهذا تصحيحٌ مهمٌّ لحجمِ المشكلة: ليست ثغرةً مفتوحةً اليوم، بل **عدمُ اتّساقٍ مقيس** يبقى إذا أُضيفَ كاتبٌ آخر (أو حُمِّلَ صفٌّ من نسخةٍ أقدم). والعاملُ الذي ينقذُه اليوم متّفقٌ في موضعٍ واحد؛ لو نُقل الحارسُ أو أُغفل، سقط.

والإصلاحُ محدَّدٌ بالكامل، وهو **تماثليٌّ بين المجالين** بوصفه شرطًا: يشترط كلُّ بناءِ معاييرَ أن تكون الحالةُ من `_POSITIVE_IDENTITY` قبل أن يُؤخَذ `email`، فيسقط صفُّ `CONFLICTING` و صفُّ `UNKNOWN` و صفُّ `لا حالةَ له` جميعًا. **وهذا تغييرٌ صغير، لكنه لم يُطبَّق في هذه الجولة** لأسبابٍ في §10.11.8.

#### 10.11.6 ختمٌ واحدٌ أم خمسة؟ — تصحيحٌ لتأطير الجولة الثالثة

الجولةُ الثالثة (§10.10.6) قالت: «الرخصةُ تُمنحُ قبل أن توجد القيمةُ التي كان يمكن وزنُها». واستخلاصُ الفحصِ أدقُّ من ذلك ويصلحُه:

```text
runtime/service.py:509   row.scenario   = scenario.model_dump(...)   ← ختمُ الفهم
runtime/service.py:527   row.identities = identities                ← ختمُ الإسناد
runtime/service.py:567   _bind_plan(...) → plan_version, plan_hash  ← ختمُ الخطة
approvals/service.py:106 intent_hash(tool, arguments, account)       ← ختمُ التفويض
tasks/service.py:121     Task(fulfillment_profile=...)               ← ختمُ النطاق
```

**خمسةُ مواضعَ ختمٍ قائمة، لا موضعٌ واحد.** والفرقُ الجوهريُّ أنّ ما يُختمُ في كلٍّ منها:

| الموضع | ما يُختم | نوعُه | متى |
| --- | --- | --- | --- |
| `Task` | النطاقُ والأدواتُ والمخاطرُ والحدود | **نطاق** | التسليم |
| `row.scenario` | نموذجُ الفهم: نيّةٌ وحدودُ الموعد | محتوى | بعد الفهم |
| `row.identities` | النتيجةُ الحتميةُ للإسناد | محتوى | بعد الإسناد |
| `plan_version`+`hash` | الخطةُ التي يعدُّها المؤشِّر | تخطيط | بعد التخطيط |
| `intent_hash` | الوسائطُ بعد التحقّق | تفويض | عند البوّابة |

**ولا واحدٌ منها يحملُ محتوى.** `TaskContractInput` **عشرةُ حقولٍ** لا غير (وكنتُ قد كِدتُ أكتبَ «إحدى عشرة» — والعدُّ الصريح يردُّها إلى عشرة)، وهي: `goal` (نصُّ المستخدم) و`success_criteria` (نثر) و`fulfillment_profile` و`allowed_tools` و`risk_policy` و`deadline` و`max_cost` و`max_steps` و`verification_method` و`fallback` — **ولا حقلَ محتَويَ واحدًا**، ولا في أيّ موضعٍ من الخمسة. فالتشخيصُ الأدقُّ ليس «الرخصةُ تسبقُ القيمة»، بل:

> **لا يوجد ختمُ محتوى في طبقةِ النطاق، في أيّ لحظة، ولا في أيّ موضع.**

و`Task.fulfillment_profile` ليس ختمَ محتوى بل **خَيارُ نطاقٍ**: «أيُّ سؤالٍ سيُطرح». وهو سؤالٌ مشروعٌ عند التسليم لأنّه يُقرأ من `goal` الحرّيّ لا من الفهم. فالاعتراضُ الزمنيُّ في §10.10.6 يصيبُ **توقيتَ اختيار المجال** لا **توقيتَ الختم**، وهذا ما يعيد ترتيبَ التصاميمِ في §10.11.7.

#### 10.11.7 التصاميمُ الثلاثةُ المرشَّحة (بلا ترتيب)

**(أ) تصنيفٌ عند التسليم، وتأكيدٌ صامتٌ عند الفهم.** يبقى `build_slice_contract` كما هو، لكنّه **يصنّف** `goal` إلى مجالٍ بحتميّ مقفول، ويفهمٌ يجب أن يُرجع `intent` **يساوي** المجالَ المختوم، وإلّا فشلت المهمّة. المحتوىُ (الموضوعُ والمتن) يُؤلَّف في الفهم ويُختم في `row.scenario` كما يُختم الـwindow. دورةُ الحياة: بلا تغييرٍ في البنية. الإنفاذ: بوّابةٌ واحدة، وكتابةٌ واحدة لـ`Task.fulfillment_profile`، و`LIVE_SEALABLE_PROFILES` كما هي. الاستدعاء: الصفوفُ المختومةُ تُقرأ ولا تُعاد. تقويمي: كما هو — بين المجالين متماثل. **الأثر**: يبقى خللُ المتنِ المختومِ غيرَ مرئيّد كما هو، **وخللُ القائئِ في §10.11.5 مستقلُّ عن هذا التصمُّر تمامًا** ويُصلَح بمفرده — كما في (ج) لا كما هنا.**: يُحلُّ خللُ القارئ، ويبقى خللُ المتنِ المختومِ غيرَ مرئيٍّ كما هو. **الكلفة**: تصنيفٌ مزدوجٌ في موضعين مربوطَين بتأكيدٍ صامت، **والبوّابةُ مغلقةٌ على الشرط B**.

**(ب) مسرودُ إرسالٍ مُرسلٌ (Sealed Send Intent) بعد الإسناد.** طبقةُ النطاق تبقى كما هي **تمامًا** — لا تصنيفَ ولا تأكيد. بعد الإسناد وقبل التخطيط، يُختم شيءٌ واحدٌ على صفّ التنفيذ: `{recipients, subject, body}`، بصاحبِ تأليفٍ معلَنٍ لكلِّ قيمة. و`intent_hash` يربطُ ذلك المسرودَ بدلَ قاموسِ وسائطٍ يُبنى عند البوّابة. الإنفاذ: بوّابةٌ واحدة، وموافقةٌ واحدة، ولا مسارَ ختمٍ ثانٍ. **الكلفة**: ختمٌ سادس (مسرودٌ محتَوٍ)، و`migration` لعمودٍ جديد، و**مفرداتُ تأليفٍ جديدة** (`USER_LITERAL` / `MODEL_GENERATED` / `DERIVED`)، وهي بحدِّ ذاتها إجابةٌ غيرُ مكتوبة. تقويمُ Calendar: لا يُمَسّ. **البوّابةُ مغلقةٌ على A وB وD معًا**.

**(ج) تضييقُ السطح: يبقى الإرسالُ للعميل المُصادَق عليه.** لا فرعَ gmail في الـruntime، و`gmail_send` يبقى في الفهرس للاستعمالِ المباشر وخارجهَ عن `LIVE_SEALABLE_PROFILES`. المسارُ الحيُّ الوحيدُ يبقى `POST /gmail/send` بحروفِ المستخدم الثلاثة. الإنفاذ: تفويضُ الحسابِ بـ`(tenant_id, user_id)` لا بالسياسة — وهذا **مستخدمٌ على حسابِه، لا وكيلٌ يعملُ نيابةً عن المستخدم**، وهو فرقٌ جوهريٌّ لا تقنية. الاستدعاء: لا ينطبق. تقويمُ Calendar: لا يُمَسّ. **الأثر**: لا يستطيع الوكيلُ أن يرسل بريدًا، وخللُ القارئ في §10.11.5 وخللُ `email` في §10.11.4 **مستقلّانِ عن هذا التصوُّرِ تمامًا** ويُصلَحان بمفردهما. **الكلفة: صفر.**

### 10.12 الجولةُ الخامسة: سلامةُ الهوية الدلالية وربطُ الموافقة (Identity Semantic Integrity + Approval Binding)

الجولةُ الرابعة (§10.11) قِست خللَين ثمّ علّقتهما: قاعِدَةُ الإسنادِ في السطر 175 تَعُدُّ **المطابقات** لا **الكيانات**، والقارئان في `runtime/fulfillment.py` يأخذان `email` ولا يقرآن `status`. 그리고 كتبت في §10.11.9 أنّ أوّلَ بندٍ في الحدّ التالي هو «تصحيحُ السطر 175 **وتشديدُ قارئَي المعايير**».

**وتلك الجولةُ تسحب نصفَ «FIRST NEXT» الذي كانت تركتُه — تصحيحُ قارئَي المعايير — لأنّ الفحصَ الجديدَ يثبتُ أنّ نصفَه **في الموضعِ الخطأ**.**

#### 10.12.1 الحارسُ واحدٌ لا ثلاثة، والدليلُ بالإفراغ

الادّعاءُ الذي تحمّله الجولةُ الرابعة: «الكاتبُ صارمٌ والقارئُ لا». والادّعاءُ الأدقُّ: **لا يوجد كاتبُ ثانٍ أصلًا**. فحصُ كلِّ إسنادٍ لعمود `identities` في `src/` كاملًا وفي `alembic/` كاملًا يُخرجُ **موضعًا واحدًا**:

| الموضع | ما هو | موقعُه |
| --- | --- | --- |
| بناءُ الصفّ | `identities=[]` | `runtime/service.py:297` |
| **الكتابةُ الوحيدة** | `row.identities = identities` | `runtime/service.py:527` |
| القراءةُ الأولى | `identities = list(row.identities)` | `runtime/service.py:718` (في `_execute`) |
| القراءةُ الثانية | `identities=list(row.identities)` | `runtime/service.py:983` (في `_settle_verification`) |

و`alembic/versions/e9f8a7b6c5d4_add_runtime_executions.py` **يُعرِّفُ العمودَ ولا يزرعُه**. فلا بذرة، ولا `fixture`، ولا هجرةٌ، ولا مسارُ تعافٍ يكتبُ صفًّا ثانيًا.

وثلاثةُ مستهلكين يقرأون من نقطتَي القراءة لا غير:

| المستهلك | ما يبنيه | موقعُه |
| --- | --- | --- |
| `_intents_for` | `attendee_emails` التي تصل `calendar.create_event` | `runtime/service.py:1109` |
| `_fulfillment_outcome` → `calendar_meeting_criteria` | `required_attendees` | `runtime/service.py:1535` |
| `_fulfillment_outcome` → `gmail_send_criteria` | `required_recipients` | `runtime/service.py:1560` |

**فشكلُ الثابت هو: بوّابةٌ واحدة، ثلاثةُ مستهلكين.** وحارسُها 686 يرفع `RuntimeFatal`، و`except` في 526 يحوّله إلى `_fail` **قبل** السطر 527. أي أنّه **لا يمكن كتابةُ صفٍّ غيرِ موجبٍ على المسارِ الحيّ، بالبناء لا بالاتّفاق**.

#### 10.12.2 سحبُ إصلاحِ الجولة الرابعة: القارئُ ليس موضعَ الحارس

الإصلاحُ الذي اقترحته الجولةُ الرابعة — «يشترط كلُّ بناءِ معاييرَ أن تكون الحالةُ من `_POSITIVE_IDENTITY` قبل أن يُؤخَذ `email`» — **مسحوبٌ في هذه الجولة**، لثلاثةِ أسبابَ في المستودع نفسِه لا في الذوق:

1. **المستودعُ ينصّ على Contra.** `tests/test_intent_provenance.py::test_how_an_identity_was_established_is_not_part_of_the_criteria` يثبّت أنّ `status` و`confidence` **يجب ألّا يصل** إلى المعايير، ويقول في توثيقه: «the runtime refuses to run at all unless every guest resolved to a positive identity, so by the time a verdict is possible the establishing evidence has already done its work. Carrying it into the criteria would state a condition the evaluator could never see».
2. **الاختباراتُ تعتمدُ على ذلك.** `tests/test_fulfillment.py` و`tests/test_gmail_fulfillment.py` يمرّران صفوفًا **بلا `status` أصلًا** — مثل `identities=[{"email": "ahmed@example.com"}]` — ويطلبان ختمَ العنوان. وإضافةُ شرطِ الحالة **تكسرها**.
3. **المعيارُ لا يملكُ ما يحكمُ به.** `required_attendees` سؤالُه «هل العنوانُ مختوم؟»؛ وسؤالُ الهويةِ «هل هذا العنوانُ مُسنَد؟». خلطُهما يجعلُ المُقيِّمَ يدّعي شرطًا لا يطَّرِفُه.

**فعدمُ تماثلِ القارئ ليس خللًا في القارئ**: هو قارئُ **قيمةٍ مختومةٍ ببوّابةٍ في موضعٍ أعلى**. والخطرُ الحقيقيُّ ليس «ثلاثةُ قراءٍ بلا حارس»، بل **أنَّ جملةً واحدةً `service.py:527` تحملُ خاصّيةَ أمانٍ كاملةً، ولا شيءَ في المستودعِ يمنع أحدًا من تعطيلها لاحقًا**. وهذا ما يستحقُّ التثبيت، لا التكرار.

#### 10.12.3 حالةُ الكيان مقابل حالةِ المطابقة — الخللُ الباقي

والقياسُ نفسُه لا يزالُ قائمًا، والخللُ في **السطر 175** لم يتغيّر:

| الحالة | المطابقات | الكيانات | `status` | `confidence` | `email` | `contact_id` |
| --- | --- | --- | --- | --- | --- | --- |
| مُؤكَّدٌ بمُعرِّفَين، كيانٌ واحد | ٢ | **١** | `UNKNOWN` | `0.0` | ✔ | `people/1` |
| كيانانِ مختلفان | ١+١ | **٢** | `CONFLICTING` | — | ✔ | `None` |
| مطابقةٌ واحدة، كيانٌ واحد | ١ | ١ | `CONTACT_MATCH` | > الأولى | ✔ | `people/1` |

**أقوى الأدلّةِ في النظام هي الدليلُ الذي يُنزِّلُ الحكم**: جهةٌ واحدةٌ طابقت بـ`email` وبـ`phone` معًا — وهو ما يكافئه `derive_confidence` صراحةً — تهبط إلى `UNKNOWN` بصفرِ ثقة، **مع بقاء العنوانِ معبَّأً على النتيجة**. وقاعدةُ التعارض في `_has_conflict` قبلَها بشاشةٍ واحدةٍ تعدُّ **الكياناتِ المتمايزة**، فالمقياسان يختلفان، والخلافُ يقعُ على الحالةِ المُؤكَّدة.

العلاجُ سطرٌ واحد: `len(distinct_ids) == 1` بدل `len(exact_claims) == 1`، و`distinct_ids` محسوبٌ في السطر التالي أصلًا. **ولم يُطبَّق**، لأنّ السؤالَ «هل تُعامَل الحالةُ المُؤكَّدةُ كـ`CONTACT_MATCH` أم كحالةٍ موجبةٍ منفصلة؟» قرارٌ في **منهج الإسناد** لا في الحدِّ التشغيليّ.

**ومفرداتُ الحالة لا تحتاجُ إلى النمو**: المجموعةُ الموجبةُ ثلاثيةٌ — `CONTACT_MATCH` و`PROVIDER_VERIFIED` و`CHANNEL_VERIFIED` — تختلفُ في **المصدر** لا في **السلطة**، ثمّ تنطوي كلُّها على `VERIFIED` في السياسة. فلا «حالةً واحدة» ولا «حالةً جديدة»: ثلاثُ حالاتٍ موجودةٌ سلفًا، وكلُّها موجبة.

#### 10.12.4 الاستدعاء: لا ترقيةَ للسلطة

`_drive:517` يُعيدُ الإسنادَ **ما دامَ الصفُّ فارغًا** فقط:

* صفٌّ مختومٌ غيرُ فارغٍ **يُعادُ استخدامه حرفيًّا**؛ `resolver.resolve` لا يُستدعى في `_settle_verification` ولا في `_fulfillment_outcome`، فالحالةُ لا تُعاد قرارُها إلى موجبة.
* فشلُ الإسنادِ **لم يكتب شيئًا** (526 قبل 527)، فالصفُّ الفارغُ يُعادُ إسنادُه من الصفر، ولا يرثُ سلطةً جزئية.

**الخلاصة: لا مسارَ برمجيٍّ في المستودعِ يحوِّلُ هويةً فاشلةً أو غيرَ موجبةٍ إلى مستقبِلٍ صالح.** والطريقُ الوحيدُ لذلك كتابةٌ خارجُ النطاق إلى عمود JSON — نسخةٌ أقدمُ من هذا الكود، أو يدٌ بشرية. ولهذا السبب تحديدًا **لا يُغلقُ تكرارُ القاعدةِ في ثلاثة قراءٍ هذا الطريق**؛ كان سيُضيفُ ثلاثةَ مواضعَ للنسيان، ويبقي الجملةَ `527` بلا مراقب.

#### 10.12.5 الموافقة: ما يُربط، وما يُرى

`canonical_payload` (`approvals/service.py`) ثلاثةُ مفاتيحَ لا رابعَ لها:

```text
{"tool": <اسم الأداة>, "arguments": <كلُّ الوسائط بعد التحقّق>, "account": <account_id أو null>}
```

**فالرمزُ يُصرِّحُ باستدعاءٍ واحدٍ لأداةٍ واحدةٍ بكائنِ وسائطٍ واحدٍ على حسابٍ واحد.** وهو **لا يربط** `Task` ولا `Contract` ولا `Plan` ولا `Evidence` ولا `deadline`: تلك كائناتٌ مستقلّةٌ ببصماتِها، وصفُّ الموافقةُ يحمل `task_id` **إحالةً لا لقطة**. فالموافِقُ يقرّرُ عن **فعل**، والفعلُ هو ما لا يتغيّر. (`tool` و`arguments` و`account` هي **كلُّ** ما في البصمة.)

و`build_request_summary` و`canonical_payload` يُسمّيان من `request()` **بـ`arguments` المُتحقَّقَ منها نفسِها**، فالملخّصُ لا ينحرفُ عن البصمة، وكلُّ حقلٍ يُعرضُ داخلَها. والحقولُ التي يُسقطُها الملخّصُ **ما تزالُ مربوطة**؛ الضيّقُ في العرضِ وحدَه.

والاستهلاكُ `ApprovalService.consume` يُعيدُ اشتقاقَ `intent_hash` من الوسائطِ الحيّة ويقارنُها في **جملةٍ واحدة** مع `Approval.intent_hash == expected` و`consumed_at.is_(None)` و`Approval.status == APPROVED`، فموافقةٌ لا تُنشرُ على فعلٍ مُغيَّر.

#### 10.12.6 الرؤيةُ بالعدّ: لماذا تصمدُ اليوم، ولماذا ليست بنيةً

الشرطُ السادسُ يجيبُه **جدولُ عدٍّ**، لا الحجّة:

| الأداة | الخطر | الحقولُ المُخفاة عن الملخّص | هل تصل موافقةً؟ |
| --- | --- | --- | --- |
| `contacts.match` | LOW | — | لا |
| `calendar.read_slots` | LOW | `day_start`، `day_end` | لا |
| `calendar.get_event` | LOW | `event_id` | لا |
| **`calendar.create_event`** | **MEDIUM** | **لا شيء** | **نعم** |
| `gmail.send` *(خارجُ المقطع)* | MEDIUM | `body` | — |

**فكلُّ وسيطٍ يصل موافقةً على أيّ مسارٍ حيٍّ يراه تلك الموافقة.** الأداتان اللتان تخفيان وسيطًا `LOW` فلا تُصعَّدان أبدًا، فليس لإخفائهما أثر. و`calendar.create_event` وحدها `MEDIUM` في المقطع، وهي التي **لا تخفي شيئًا**.

**لكنّ هذه نتيجةُ تقاطعِ قائمةِ حقولٍ مع عتبةِ الخطر، لا خاصّيةٌ بنيويّة.** ويظهرُ ذلك في سطرين:

* `_SENSITIVE_ARG_FIELDS = {body, body_html, content, message}` **مُعلَنٌ في `approvals/service.py:63` ومُستعمَلٌ في لا موضع**؛ فهو يسجّل نيّةَ الإخفاء ولا يفرضُه.
* `ScheduleContentAuthorizer` يقرّرُ على `content_category` ويقرأُ `context.metadata` **ولا يقرأُ المتنَ قط** — ويُصرّحُ توثيقُه بذلك: «the message body (`arguments`) is deliberately never read». و`content_category_for(tool_name)` يشتقُّ الفئةَ من **اسمِ الأداة وحده** ولا يُخرجُ إلّا `confirm_meeting` أو `propose_time`.

**فمُجتازُ بوّابةِ المحتوىِ ليس موافقةَ مقروءة.** وهو سؤالٌ مختلف.

#### 10.12.7 التصاميمُ الثلاثةُ المرشَّحة (بلا ترتيب)

**(أ) تثبيتُ البوّابةِ الواحدة بدلَ تكرارها.** فحصُ آليٌّ لكلِّ مواضعِ الكتابة إلى `identities` في `src/` و`alembic/`، وفحصٌ آليٌّ لترتيبِ `assert call < failure < write` داخل `_drive`. هذا **تقنيةٌ لا تغييرَ سلوكٍ**: يبقى السلوكُ كما هو، ويصبحُ **انزياحُ الحارسِ أو ظهورُ كاتبٍ ثانٍ خطأً صريحًا** بدل أن يكون فخًّا صامتًا. **الكلفة: صفر في الإنتاج** (اختبارٌ فقط). **الأثر**: الخللُ في §10.12.3 يبقى؛ وخللُ القراءةِ في §10.12.2 **ليس خللًا أصلًا** فلا إصلاحَ له. **الحدُّ**: لا يُصلحُ شيئًا؛ يجعلُ الصمتَ مسموعًا.

**(ب) تصحيحُ السطر 175 وحده.** `elif len(exact_claims) == 1:` ← `elif len(distinct_ids) == 1:`، و`distinct_ids` محسوبٌ في السطر التالي. **تغييرٌ في سطرٍ واحد، صفرُ هياكل، صفرُ مفردات.** النتيجةُ أنّ جهةً واحدةً طابقت بمُعرِّفَين تصير `CONTACT_MATCH`، وأنّ **مقياسَ التعارضِ ومقياسَ الحالةِ صارا واحدًا**. **الكلفة السلوكية: صفر**. **البوّابةُ مغلقةٌ على §10.12.3 وحده**: هذا قرارٌ في منهج الإسناد، ولا يمسّ شيئًا من المتن ولا من الموافقة — **وإنّ كان ذلك كافيًا وحدَه، فهو قابلٌ للتنفيذِ منفردًا**.

**(ج) إظهارُ المتنِ في الملخّص.** `body` ينضمّ إلى `_SUMMARY_ARG_FIELDS`، فتصير الموافقةُ مُطّلعة. **الكلفة السلوكية: صفر**، والبوّابةُ تبقى على `gmail.send` مُغلقة. **لكنّها تُجيبُ عن B بسؤالٍ واحدٍ فحسب** («نُظهره»)، لا عن A ولا D ولا E، **وتقتطعُ نصًّا حرفيًّا من نموذجٍ مولَّدٍ فتدفعُ سؤالَ الخصوصيةِ إلى الأمام** بلا مَن يقرّر. **الحدُّ**: تغييرُ دلالةِ الموافقةِ لغيرِ المجالِ الذي رُخِّص، في جولةٍ حكمُها design-only.

### 10.13 الجولةُ السادسة: حسمُ منهج الإسناد — الكيانُ لا المطابقة (Grounding Methodology: Entity, Not Claim)

الجولةُ الخامسة (§10.12) تركت بندًا واحدًا `DEFERRED`: **منهجُ الإسنادِ المُؤكَّد في السطر 175**، ووصفتْه بأنّه «قرارٌ في منهج الإسناد لا في الحدِّ التشغيليّ». وهذه الجولةُ خُصِّصت لهذا البند وحده. وسألتُ سؤالًا واحدًا: **هل وحدةُ الهوية الدلاليةُ هي المطابقةُ Claim، أم الكيانُ Entity؟** ثمّ قِستُ الجوابَ على المُحلِّلِ الحقيقيّ قبل أن أُطبِّقَ شيئًا.

#### 10.13.1 المنهجُ محسومٌ سلفًا؛ السطرُ 175 هوَ وحدَه المخالف

الجوابُ لم يكن اختيارًا بين مذاهب. **المستودعُ نفسُه ينصّ على المنهج، في ستّةِ مواضعَ مستقلّة، كلُّها تتّفق:**

| # | الموضع | ما يقوله بالنصّ |
| --- | --- | --- |
| 1 | `identity/models.py` · `IdentityStatus` | «the deterministic verdict the resolver can vouch for about **one entity**» |
| 2 | `identity/service.py` · `resolve` | «Resolve **one entity** against trustable sources» |
| 3 | `identity/service.py` · `_Claim` | مطابقةُ **مُعرِّفٍ واحدٍ** بدقّة |
| 4 | `identity/models.py` · `IdentityResult` | كائنٌ **أحاديّ القيمة** بنيويًّا: `contact_id` واحد، `email` واحد، `phone` واحد |
| 5 | `identity/models.py` · `derive_confidence` | تأييدُ مصادرَ متعدّدةٍ **مكافأة**: `min(1.0, base + 0.1)` — ولا شيءَ فيه يُنقصُ الثقةَ لزيادة التأكيد |
| 6 | `identity/service.py` · `_has_conflict` | C1 يعدُّ **الكياناتِ المتمايزة** على `Contact.resource_name` |

**والنقطةُ الحاسمةُ السابعةُ ليست في الوثائق بل في كائنِ النتيجة نفسِه:** `_build` (السطر 251) كانت تحسب `distinct_ids` من نفسِ المجموعة، وتستخدمها لاشتقاق `contact_id`. فقبل التصحيح كان المُحلِّلُ يَسألُ سؤالَه الواحدَ بطريقتين — `status` بالمطابقات، و`contact_id` للكيانات — **فكان كائنُ قيمةٍ واحدٌ ينكر وجودَ نفسِه**: `status=UNKNOWN` و`contact_id="people/1"` و`email` معبَّأ، في آنٍ واحد.

فالسطرُ 175 لم يكن **قرارًا مختلفًا** عن بقيةِ المستودع. كان **الاستثناءَ الوحيدَ**.

#### 10.13.2 جدولُ الحقيقة المقيس

كلُّ صفٍّ مُقيسٌ على `IdentityResolver` الحقيقيّ عبر `GoogleBackend`، لا مستنتَج:

| الحالة | المدخلات | المطابقات | الكيانات | `status` | `confidence` | `email` | `contact_id` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| كيانٌ واحد، مُعرِّفٌ واحد | `email` | ١ | ١ | `CONTACT_MATCH` | `0.5` | ✔ | `people/1` |
| كيانٌ واحد، مُعرِّفان | `email` + `phone` | **٢** | ١ | `CONTACT_MATCH` | `0.5` | ✔ | `people/1` |
| كيانان مختلفان | `email`+`phone` | ٢ | **٢** | `CONFLICTING` | `0.0` | ✔ | `None` |
| مُعرِّفٌ واحد، كيانان | `email` | ٢ | **٢** | `CONFLICTING` | `0.0` | ✔ | `None` |
| الاسمُ وحده | `name` | ٠ | — | `UNKNOWN` | `0.0` | `None` | `None` |
| مُعرِّفٌ غائب | `email=zed@…` | ٠ | — | `UNKNOWN` | `0.0` | `None` | `None` |
| لا مُعرِّف | `IdentityQuery()` | ٠ | — | `UNKNOWN` | `0.0` | `None` | `None` |
| هويةُ مزوِّد | `provider` + `sub` | — | — | `PROVIDER_VERIFIED` | `0.9` | ✔ | `people/1` |
| هويةُ قناة | `channel` + `subject` | — | — | `CHANNEL_VERIFIED` | `0.9` | ✔ | `people/1` |
| تعارضُ حسابٍ مربوط | حسابٌ + `email` أجنبيّ | ١ | ١ | `CONFLICTING` | `0.0` | ✔ | `None` |

ثلاثةُ استخلاصاتٍ من الجدول:

1. **العدمُ يبقى عدمًا.** صفرُ مطابقاتٍ يعني صفرَ كيانات، فلا شيءَ positives. و`name` **لا يُنتج مطابقةً أبدًا** — `_exact_claims` يقرأ `email` و`phone` فقط.
2. **`confidence = 0.5` للمُؤكَّد، لا أكثر.** عرَضُ `email`+`phone` على جهةٍ واحدةٍ ليس «مصدرين مستقلّين»، فمكافأةُ `derive_confidence` لا تنطبق (هي ت-keys على **المصدر** لا على عدد المطابقات). وهذه **صحيحة**: الدليلُ واحدٌ من مصدرٍ واحد، مؤكَّدٌ بمُعرِّفَين.
3. **تناقضُ الحسابِ المربوطِ يبقى `CONFLICTING` مستقلًّا عن عدد المطابقات** (الصفّ العاشر): بنودُ C2/C5 تختبرُ **الاتّساقَ مع الحساب** لا عددَ المطابقات.

#### 10.13.3 التماثلُ الذي يقومُ عليه المنهج

| | مطابقتان على كيانٍ واحد | كيانان مختلفان |
| --- | --- | --- |
| ما تتّفق عليه | المطابقتان | لا شيء |
| ما تختلفان فيه | — | **من هو** |
| الحكم | مطابقةٌ واحدة، مُسنَدةً مرّتين | تنافُسٌ على «من» |
| الحالة | `CONTACT_MATCH` | `CONFLICTING` |

**الجوابُ عن A: نعم، ثمّة فرقٌ جوهريّ.** مطابقتان على جهةٍ واحدةٍ assertٌ واحدٌ عن شخصٍ واحد، مؤكَّدٌ مرّتين. وكيانان assertانِ مختلفانِ عن شخصين، فالحلُّ يجبُ ألّا يختار — وهذا `CONFLICTING` بالاسم. والمستودعُ **مُطبِّقٌ لهذا التماثلِ من قبلُ في موضعين**: C1 يعدُّ الكيانات، و`derive_confidence` يُكافئُ التأكيد. لم يكن سوى **سطرِ الحالة** في الجانبِ الخطأ.

#### 10.13.4 الجوابُ عن B: لا، ولا حالةَ جديدة

المُعالَجُ مفرداتُ الحالة نفسِها. `CONTACT_MATCH` مُعرَّفٌ في `identity/models.py` بأنه «a trusted identifier (exact email or exact phone) appears in the tenant's Google Contacts» — **مُعرِّفانِ على جهةٍ واحدةٍ يُحقِّقان هذا التعريفَ مرّتين**، لا مرّةً ونصفًا. فالحالةُ الموجودةُ سلفًا هي الصحيحة.

والحاسمُ بنيويًّا: `IdentityStatus` و`IdentityStatus` في `policy/models.py` **إ脸的َ مفرداتٍ مختلفتان**، `_IDENTITY_TO_POLICY` جسرُهما الوحيد، وهي **تامّةٌ على الخمسةِ إلى الثلاثة**. فأيُّ حالةٍ جديدةٍ كان لا بدَّ أن تنطوي على `VERIFIED` أو `UNKNOWN` أو `CONFLICTING` — أي **مرادفٌ** لأحدها. **فلا «حالةً واحدة» ولا «حالةً جديدة».**

#### 10.13.5 الأثرُ على السياسة: صفر

`CONTACT_MATCH` كان ينطوي على `VERIFIED` **قبل** هذه الجولة، والخريطةُ لم تُعَدَّ توجيهًا:

| `IdentityStatus` (المُحلِّل) | `policy.IdentityStatus` | `rule_identity` عند MEDIUM+ |
| --- | --- | --- |
| `CONTACT_MATCH` | `VERIFIED` | `ALLOW` |
| `PROVIDER_VERIFIED` | `VERIFIED` | `ALLOW` |
| `CHANNEL_VERIFIED` | `VERIFIED` | `ALLOW` |
| `UNKNOWN` | `UNKNOWN` | `REQUIRE_APPROVAL` |
| `CONFLICTING` | `CONFLICTING` | `DENY` |

**فالتغييرُ يزيلُ تصعيدًا افتراضيًّا لحالةٍ لم تكن تُنتَجُ أصلًا (انظر 10.13.6)، ولا يَلمسُ الترويسةَ ولا العناوينَ ولا الرميَ ولا التقويمَ، ولا `_fulfillment_outcome`، ولا `PolicyEngine`.**

#### 10.13.6 نصفُ الانفجار: صفر

هذا هو القياسُ الذي حوّل «التصحيحُ آمن» من دعوى إلى نتيجة. **النتيجةُ بمُعرِّفَين تتطلّب استعلامًا يحمل `email` **و**`phone` معًا.** وفحصُ كلِّ موضعٍ يُبنى فيه `IdentityQuery` في المستودع كلِّه يُخرج **موضعين اثنَين** لا غير:

| الموضع | ما يُنشئه | لماذا لا يبلغ مُعرِّفَين |
| --- | --- | --- |
| `runtime/service.py:675` | `IdentityQuery(email=email) if email else IdentityQuery(name=guest)` | لا `phone` |
| `runtime/service.py:1118` | `IdentityQuery(email=emails[0])` | لا `phone` |

و`_exact_claims` لا يقرأ إلّا `email` و`phone`؛ فلا `name` ولا `provider` ولا `channel` تُنتج مطابقة. **فالفرعُ المصحَّحُ كان غيرَ قابلٍ للوصول على أيِّ مسارٍ حيّ.** وهذا سببُ 안전تِه، **وهو أيضًا الفخُّ**: أوّلُ مَن يضيفُ `phone` إلى استعلامِ الضيفِ كان سيحصل على `UNKNOWN` كاذبةٍ لأحسنِ جهةٍ مؤكَّدةٍ في دفترِ العناوين، **ولEREت كأعطالِ مُحلِّلٍ لا كقياسٍ خاطئ**. وهذا ما ثبّته `test_no_product_query_can_yield_two_claims_so_the_correction_is_latent` صراحةً، لأنّ **إصلاحًا كامنًا هو.netty يُعاد التراجعُ عنه بهدوء.**

### 10.14 الجولةُ السابعة: البوّابةُ الوحيدةُ آليًّا (Single-Gate Lock: One Writer, Observed Order)

§10.13.8 صِرفَ التصميمُ 2 إلى «مؤجَّل»، و§10.13.10 حدَّد الحدَّ الآتي: `identities` كاتبٌ واحد · `assert call < failure < write`. وهذه الجولةُ خُصِّصت له، **بصفرِ تغييرٍ في الإنتاج**.

الحارسان القائمان حقيقيّان وباقيان. لكنّهما لا يبلغان ما تحتاجه الخاصّية، وقد **قِستُ الفجوةَ بكسرِ `runtime/service.py` عمدًا** لا بالاستنتاج:

| # | الكسرُ المدخَل | الحارسُ القديم | حارسُ هذه الجولة |
| --- | --- | --- | --- |
| 1 | `row.identities.append(...)` بجوار الكاتب | **نجح ١٢/١٢** | كابِطٌ على الكتابة الثانية |
| 2 | رفعُ الكتابة فوق `try` | اختبارُ الترتيب **نجح** | سجَّل `write` **قبل** `call` |
| 3 | `except RuntimeFatal` لم يعد `return`-ing | كابِطٌ | كابِطٌ |

فالسطرُ الأوّلُ يقول إنّ تعبيرًا نمطيًّا واحدًا على صيغة الإسناد **لا يرى نصفَ أشكال الكتابة**، والثاني يقول إنّ مقارنةَ مواضعَ نصّية **تُثبت ترتيبَ النصّ لا ترتيبَ التنفيذ**. والثالثُ يقول إنّ الجديد أقوى لا وحيد.

#### 10.14.1 تعريفُ الكاتب، والجردُ المقيس

**الكاتب** — مُعرَّفٌ في `classify_writes` — هو أي موضع نحويّ يستطيع تغيير القيمة المحفوظة للعمود: إسنادٌ أو `+=` أو `del` عبر السمة أو عبر الفهرس، أو تحويرٌ في الموضع (`append`، `extend`، `update`، …)، أو `setattr`، أو `identities` في دالّةِ DML، أو SQL خام. ثم **الجردُ fail-closed**: كلُّ موضع `identities=` يجب أن يكون مُدرجًا في قائمة القراءة، وإلا فشِل البناء.

المسحُ يقرأ **١٢٩ ملفَّ Python** تحت `src/` و`alembic/`. والنتيجةُ واحد:

| الموضع | الشكل | الحكم |
| --- | --- | --- |
| `runtime/service.py:527` | `attribute-assign` | **الكاتبُ الوحيد** |
| `runtime/service.py:297` | `identities=[]` | تهيئةُ صفٍّ بقائمةٍ فارغة — لا كاتبُ قيمة |
| `api/runtime.py:104` | قراءةُ الصفّ | إسقاطٌ مُنقَّى |
| `runtime/service.py:772` · `983` · `1538` · `1562` | قراءة | إسقاطٌ · إسقاطُ نتيجة · معياران |

وكلُّ موضعٍ من الخمسة **مُثبَتٌ باسمِ الدالّةِ التي يقعُ فيها**، فالقائمةُ تقول «هذا داخل `_execute`»، لا «هذا السطرُ ما زال موجودًا». ولا وجودَ لـDML أو `setattr` أو SQL خام، ولا ترحيلِ بياناتٍ في الـ١١ هجرة؛ والعمودُ غيرُ قابلٍ لـNULL، وقيمتُه الافتراضيّة `'[]'::jsonb` عند القاعدة — فحتى صفٌّ أُدخل خارجَ ORM يبدأُ فارغًا.

#### 10.14.2 الترتيبُ مُقيسًا، لا مقروءًا

لم تعد المقارنةُ على `string.index()`. التشغيلُ الحقيقيُّ لـ`_drive` على صفٍّ حقيقيّ، والمُحلِّلُ الحقيقيُّ والـcontacts الحقيقيُّ يقرّران النتيجة، و`set`-listener على العمود يسجّل كلَّ كتابةٍ مع **السطرِ الذي نفَّذها**:

| المسار | الأحداث المُلتقطة | `row.identities` |
| --- | --- | --- |
| الضيفُ قابلٌ للإسناد | `call@522` → `write@527` ← `failure@560` | مطابِقٌ واحد · `CONTACT_MATCH` · `0.5` |
| الضيفُ غيرُ قابل | `call@522` → `failure@526` | **`[]`** |

السطرُ ٥٢٦ هو البوّابةُ نفسُها، ومعروضةٌ **بنيويًّا** لا بنصٍّ: معالِجٌ واحدٌ يلتقط `RuntimeFatal` **و**يفوّض إلى `_fail`. والصفرُ في العمودِ الثاني **مقيسٌ لا مفترَض**: نفسُ الـlistener الذي رآه يكتبُ في السطرِ الأول يعرض هنا **لا شيء**، لأنّ لا شيءَ كتب.

وثالثُ اختبارٍ يقلبُ السؤال: صفٌّ مُختومٌ يُعادُ تشغيلُه فلا يُعادُ إسنادُه ولا يُكتبُ ثانيةً — فالخاصّيةُ واحدةٌ من الجهتين.

#### 10.14.3 حالةُ الجولة السابعة

| --- | --- |

| **الاختباراتُ الجديدة** | `tests/test_identity_single_gate_lock.py` (١٠ اختبارات): كاتبٌ واحد · البذرةُ الفارغة · لا DML · قائمةُ القراءة · الضابطُ السلبيّ (١٧ شكلًا) · الترتيبُ المقيس · مسارُ الفشل · عدمُ إعادة الكتابة · جمودُ الدلالات · ليست خاصّيةَ ملفِّ الاختبار |

### 10.15 الجولةُ الثامنة: القراراتُ المعلَّقة (Gmail Authorship & Approver Visibility — Settling the Deferred Decisions)

القسمُ 10.11 قاسَ المقدماتِ ثم **توقَّف عمدًا**، وختمَ بجملةٍ صريحة: «يثبّتُ المقدماتِ التي يجب أن تتحرّكَ بها جولةٌ تُحسِّم A و B و D و E». تلك هي هذه الجولة. لم تُضِف سطرًا في الإنتاج، ولم تفتح `gmail_send`، ثلاثُ نتائجَ جديدة:

**١. سطحُ الموافق عليه أدقُّ من Payload الذي يوافق عليه — والإخفاءُ ليس حقلًا واحدًا.** الجولةُ السابقة أظهرت أنّ `body` مربوطٌ ومستورٌ. لكنها لم تقس **شكل** الفجوة. `build_request_summary` يأخذ `(tool, arguments)` ولا شيءَ غيرَ ذلك، فخمسةُ أجسامٍ متمايزة تنطبقُ إلى **ملخّصٍ واحد** بينما `intent_hash` يُنتج **خمسةَ بصماتٍ متمايزة**. الموسمُ ليس «معاينةً منقوصة» للقصد، بل **إسقاطًا متعدِّدَ الواحد إلى واحدٍ فوقPayload نفسِه**. نتيجتان تلتزمان هاتين ولا تُفترَضان:

| القيمة | مربوطةٌ في `canonical_payload`؟ | قابلةٌ للتصييرِ في الملخّص؟ |
| --- | --- | --- |
| `to` · `subject` | نعم | **نعم** |
| `body` | نعم | **لا** |
| `account` (صندوقُ الإرسال `From:`) | **نعم** | **لا — وليست في التوقيع أصلًا** |

الخطرُ المتعلِّقُ بالحساب أشدُّ من نقصِ `body`: الحقلُ الذي يحدّد **مَن** يخرج الرسالةَ باسمه **لا يستطيع** أن يكون معاملًا في الأداة (وهو موضعُ المستودع الصحيح)، **ومربوطٌ** بالبصمة، **ومخفيٌّ** عن القارئ. و`ApprovalDecisionRequest` يحمل `reason` اختياريًّا واحدًا مع `extra="forbid"`، والـAPI يقيّد القرارَ بـ`current.id` — وهو نفسُ `user_id` الذي أُنشئت بموجبه الصفُّ. فالموافقةُ **ذاتيةٌ بنيويًّا**: لا يوجد قارئٌ ثانٍ في المكدّس، لا بالإهمال بل بالتصميم.

**٢. خللُ الهوية له مُنتِجٌ لا قارئٌ فقط.** الجولةُ السابقة قاست قارئاتِ المعايير بصفوفٍ مكتوبةٍ بيدها (صفٌّ `CONFLICTING`، صفٌّ `UNKNOWN`، صفٌّ بلا `status`)، ولم تسأل: **هل يستطيعُ الحلّالُ الحيُّ أن يُخرجَ صفًّا كذلك؟** يستطيع. `_has_conflict` يُعيدُ `True` لجسمين يتشاركان عنوانًا واحدًا، ووثيقتُه تعد بـ«CONFLICTING never picks a winner» — لكن `_build` يحسبُ `email` في فرع `else` من شرطٍ يستثني **فقط** `PROVIDER_VERIFIED` و`CHANNEL_VERIFIED`. فحكمُ `CONFLICTING` يخرجُ حاملًا عنوانًا ملموسًا، و`contact_id` يُحجبُ صحيحًا — ولهذا التسريبُ خفيّ: النتيجةُ تبدو نصفَ محلولة. وهذا بالضبط مُدخلُ القارئ الذي يتجاهلُ `status`، فيختمُه `gmail_send_criteria` **مستلِمًا مطلوبًا**. النطاقان الآن مُقفلان **من طرفٍ إلى طرف** عبر الحلّالِ الحقيقيّ، لا كملاحظتين مستقلّتين.

**٣. الشدّةُ محدودةٌ مرّتين، والحدُّ مثبَّتٌ لا مُدَّعى.** السلسلةُ غيرُ قابلةٍ للوصول في الإنتاج لسببين مستقلّين لا يقومُ أحدُهما على الآخر: الـruntime **يرفع قبل أن يكتب** هويةً غيرَ موجبة، و`gmail_send` **ليس** في `LIVE_SEALABLE_PROFILES` فلا وجودَ لمهمةِ gmail أصلًا تحملُ ملفَّها. احذفْ أحدَهما تبقّى الآخر، واحذفْهما معًا تصيرُ ثقبًا. وثالثٌ أصغرُ يحدُّ البصمةَ نفسَها: `_canonical_value` ينتهي بـ`str(value)` — وهو **خطأُ الالتقاط** (catch-all) يحوّلُ إلى نصٍّ ما لا يعرفه، فيسمحُ لكائنين مختلفين بالتطابق — لكن حقولَ `GmailSendArgs` الثلاثةُ تُتحقَّقُ إلى `str`، فذلك **شيفرةٌ ميتةٌ في هذا المجال**، والخطرُ المتبقّي **مسجَّلٌ لا مُبالَغٌ فيه**. (وهنا مُلاحظةٌ منهجيّةٌ صريحة: أولُ محاولةٍ للتحقق في هذه الجولة كتبت `issubclass(EmailStr, str)` ففشلت — و`EmailStr` ليست صنفًا من `str` في pydantic 2.13؛ والصحيحُ هو التحققُ من قيمة `model_dump()` بعد التحقّق، وهو ما يفعله الـgateway فعلًا.)

#### 10.15.1 القراراتُ الأربعة

| السؤال | القرارُ المستقرّ | أساسُه |
| --- | --- | --- |
| **A** — مَن يكتب `body`؟ | **لا يوجد كاتبٌ في المسار الوكيل — والإجابةُ لا تُحسَم بإضافة فحص** | الاستدعاءُ الحيّ الوحيدُ `POST /gmail/send` بـ literals؛ و`PlanStep` لا يحملُ حقلَ نصٍّ؛ فمصدرُ التأليفِ غائبٌ بنيويًّا. أيُّ نظامِ تأليفٍ يستدعي **أثرًا** جديدًا (مصدرًا، استنساخًا، قيمةَ رَبط) لا شرطًا |
| **B** — رؤيةُ الموافقِ عليه | **سطحٌ حرفيٌّ فقط أو ليس موافقة** — موسَّعٌ ليشمل `account` لا `body` وحدَها | الإسقاطُ متعدِّدُ الواحد إلى واحد؛ ولا موافقةَ إن لم يكن القرارُ على نصٍّ مقروء؛ **ولا** عينَ ثانية، فالتقويةُ في الملخّص وحدَه لن تكفي |

| **D** — الغموض والتعارض | **لا حالةَ جديدة**؛ **بلّوغُ الخلل غيرُ متأخِّرٍ (defect) لا مسألةُ مفردات**؛ والإصلاحُ في **الكاتب** لا القارئ (تشديدُ الكاتب ليطابقَ القارئَ أمّا العكسُ فهو خللٌ مشوَّه) | خمسةُ أعضاءَ فقط؛ و`rule_identity` يصنعُ ثلاثةَ قرارات؛ و`AMBIGUOUS` سيكونُ مترادفًا |

#### 10.15.2 حدودٌ لم تُتجاوَز (مقصودة)

لم يُطبَّق أيُّ إصلاحٍ إنتاجي. تحديدًا: **لم** يُشدَّد `_build` ليحجب العنوانَ عند حكمٍ غيرِ موجب، و**لم** يُشرَط `status` موجبٌ في قارئي المعايير. السببُ أنّ جدّةَ الإصلاح غيرُ مُثبَتةٍ اليوم: الحارسُ في القارئِ الحيّ يمنع الصفَّ السيّئ أصلًا، والملفُّ غيرُ مرخَّص، فالسلسلةُ مُعطَّلةٌ مرّتين. وتطبيقُ الإصلاح على `calendar_meeting` — وهوُ **مرخَّصٌ حيًّا** — تغييرٌ في سلوكٍ إنتاجيّ، وقرارُ هذا الجولة design-first. فالإصلاحُ **مُصاغٌ ومحسوسٌ**، ومُرجأٌ إلى جولةٍ تحمل صريحَ مخوَّل بتغيير الإنتاج.

## 11. Memory

Memory هي Context وليست Authority.

يمكنها دعم Understanding وPlanning، لكنها لا تمنح Permission، ولا تتجاوز Policy، ولا تختار مسارًا محميًا، ولا تثبت Completion بمفردها.

**النتيجةُ الصريحة لهذه القاعدة**: قد تُمدّ Memory التنفيذَ والـresolve بمعلوماتٍ مرشَّحة — كعنوانٍ يتذكَّره النظام لضيفٍ سمّاه المستخدم — لكنها لا تصبح **سلطةَ نيّةِ مستخدم** بمجرد أن تدوم القيمةُ الناتجة في صفٍّ مختوم. دوامُ القيمة في `row.identities` يجعلها أثرًا دائمًا، لا نيّةً مطلوبة؛ فالمصدرُ يحدّد السلطة، لا الاستمرار (§10.9 و§10.10).

## 12. Verification وPersistence

Verification جزء أساسي من KAI:

```text
Provider Response → Observed Evidence → Verification → Fulfillment
```

Durable Execution أيضًا جزء أساسي، ويشمل Claims/Leases وFencing وPlan/Version Binding وAppend-only Evidence وCursor Persistence وCrash Recovery وResume وRe-derivation.

المبدأ:

> يجب فهم المهمة المستأنفة من Durable State دون الاعتماد على تذكر النموذج.

## 14. Non-Goals

لا ينبغي أن يتحول KAI إلى:
- General Workflow Engine؛
- Unrestricted Graph Runtime؛
- Model-authored Permissions؛
- Model-authored Lifecycle؛
- Memory-driven Authority؛
- Direct Model/Provider Connectivity؛
- General-purpose Programming Language؛
- State Machine ثانية مخفية داخل IR؛
- Path-specific Goal Language غير مبررة معماريًا؛
- مجموعة Primitives جديدة فقط لأن Semantics غير محسومة.

## 16. ما لم يثبت بعد؟

المحسوم في §10 ولا يُعاد طرحه: **مكان Fulfillment Authority** (طبقات، والقرار في KAI)، و**علاقة Path Termination بـIntent Fulfillment** (الانتهاء ليس تحقّقًا)، و**أن `ResultNode` لا يملك سلطة**، و**أن مَن يختار المُقيِّم هو الـSealed Contract** عبر `fulfillment_profile` (لا النموذج، ولا الخطة، ولا المسار).

الباقي غير مثبت:

1. ~~Semantic Model واحدة لـ`success_criteria` تصل سؤال الـContract بمُقيِّم~~ **مُثبت** للنطاق الواحد: `SuccessCriteria` مُصفَّف ومختوم، والمُقيِّم يقرأه لا prose (§10.5). ويبقى مفتوحًا منه: **تعميمه** على مجالات أخرى — نموذج عام، أو شجرة شروط، أو معايير يكتبها نموذج — فهذا قرارٌ معماري لم يُتخذ، ومقصود ألّا يُتَّخذ ضمن هذا المسار.
2. Post-conditions للخطوات التي تم تجاوزها.
3. Verification عامة تتجاوز الـVertical Slice.
4. ~~ربط الحكم المُسجَّل بهوية المُقيِّم وإصداره~~ **مُثبت**؛ ويبقى مفتوحًا منه: ترحيل الهوية عند تغيّر الدلالات، فسجلٌّ يعبر ذلك الحد سيقرأ `v1` رغم أنه حُسم بـ`v2`.
5. مسار إضافة مجال ثانٍ: `Literal` من مفرد واحد، بلا سجل مُقيِّمين.
6. Failure/Continue Semantics.
7. Branching بعد Failed Step.
8. Static Exhaustiveness Guarantees.
9. الحد النهائي بين Representation وRuntime Semantics.
10. ~~**Semantic Model لـEvidence تُعرِّف «المحاولة المؤهَّلة»** بدقّة: توحيد قراءة `event_id` بين `evidence` و`data` (§10.5)~~ **مُثبت** لمجال `calendar_meeting`: الحدّ في `kai/runtime/evidence.py`، و`evidence` هي المرجع بلا fallback، ويقرأه الـevaluator والـruntime والاسترجاع من موضع واحد. ويبقى منه ما لم يُطلب: تعميم على مجالات أخرى.

## 17. نقطة التجميد الحالية

حُسمت Fulfillment Authority في §10، وحُسم بعدها **الربط الصريح** بالحقل، و**استقلال الحكم عن ترتيب الأدلة**، و**هوية المُقيِّم المسجَّلة**، و**معنى النجاح كنموذج مُصفَّف**. ويبقى التجميد على **دلالتها العامة** لا على مكانها:

**لا نضيف:**
- IR Primitives جديدة؛
- Graph Semantics أوسع؛
- Loops؛
- General Workflow Features؛
- Path-specific Goal Languages؛
- Terminal State Vocabularies جديدة؛
- Skills/Domain Registry أو بروتوكول مُقيِّم (تبقى مفردات مغلقة؛) المجال الثاني تعديلٌ في العقد؛
- **لغة `success_criteria` عامة**: لا شجرة boolean، ولا predicate مسجَّل، ولا معايير من نموذج (تُنقل صراحةً إلى قرارٍ مستقل)؛
- Computer Use Architecture؛
- Desktop Agent Architecture؛
- Multi-Agent Architecture.

**ولا نرخّص للتسجيل الحي**: أيُّ `FulfillmentProfile` يحمل أقلَّ من مرساةِ نيّةِ مستخدمٍ مختومةٍ يقرّر عليها مُقيِّمه. العضويةُ في `FulfillmentProfile` ليست إذنًا؛ `gmail_send` يبقى في المفردة ولا يُرخَّص له حتى يتحقّق شرطُ المرساة (بند §10.10 واختباراه في `test_task_contract.py`).

**نركز على:**
1. ~~Semantic Model لـEvidence تُعرِّف «المحاولة المؤهَّلة» بدقّة، فتشمل توحيد قراءة `event_id` بين المُقيِّم والـruntime~~ **مُنجَز لمجال `calendar_meeting`**: الحدّ في `kai/runtime/evidence.py` بلا معرِّف محاولة، و`evidence` هي المرجع بلا fallback، ويقرأه الثلاثة من موضع واحد (§10.5).
2. Semantic Model لمجال ثانٍ — **بقرار معماري صريح**: هل يبقى معيارٌ واحد لكل مجال، أم تظهر لغة مشتركة؟ قرارٌ مؤجَّل عمدًا.
3. اختبار الفصل بين `NOT_FULFILLED` و`INDETERMINATE` على مسار حيّ في مجال يُنتجه فعلًا، لا بتدخّل.
4. ترحيل لهوية المُقيِّم إن تغيّرت الدلالات، فالسجل القارئ يُظهر إصدارات متتابعة لا إصدارًا واحدًا.
5. توثيق المعايير المُطبَّقة مع الحكم (`as_criteria()` نصٌّ للعرض فقط) إن لزم تفصيل أعمق — دون تحويله إلى مصدر.
6. تحديث الوثيقة المرجعية وفق النتيجة.

## 18. التجربة المعمارية التالية

نختبر فرضية واحدة:

> **مساران مختلفان يمكن أن يكونا طريقتين بديلتين لتحقيق نفس Intent تحت نفس Sealed Success Contract.**

مثال:

```text
Intent: جدولة اجتماع ضمن نافذة زمنية مسموحة

             Calendar Fact
                  |
            ┌─────┴─────┐
            |           |
          Path A      Path B
            |           |
        اختيار Slot 1  اختيار Slot 2
            |           |
            └─────┬─────┘
                  |
          نفس Fulfillment Contract
                  |
               Evidence
                  |
           نفس Completion
```

إذا نجح المساران تحت Contract واحد، فهذا يدعم أن Branching Alternative Execution Mechanism، وليس Goal Language.

إذا احتاج المسار إلى Goal مختلف، فيجب التحقق مما إذا كانت هناك Intentان مختلفتان موضوعتان في Task واحد.

نتيجة هذه التجربة مقيسة في §8.1: الميكانيزم PROVEN، ومثال «Slot 1 مقابل Slot 2» تحديدًا INCONCLUSIVE. وهذا الحد معرَّف معياريًا في [مواصفة KAI-IR §4.4.5](../kai-ir-spec-v0.md)، لأنه حدود مفردات الحقائق، وهي منطقة المواصفة لا الوثيقة المرجعية.

## 19. ترتيب السلطة

```text
1. Human / Explicit User Intent
2. Sealed Task Contract
3. Policy / Approval / Identity Authority
4. Deterministic Runtime وTask State Machine
5. Tool Gateway وProvider Verification
6. Durable Evidence
7. KAI-IR Representation
8. Model Proposals
9. Memory / Context
```

هذا ترتيب للسلطة وليس بالضرورة Call Order.

**ثلاثةُ سلطاتٍ تُخلط عمدًا، فيُفرَّق بينها صراحةً** (الترتيب أعلاه لا يُغيّره هذا):

```text
Independence authority      — قيمةُ معيارٍ لا تُشتق من مجموعة الأدلة نفسها
        ≠
User-intent authority       — قيمةٌ مصدرُها بيانٌ مختومٌ عمّا طُلب
        ≠
Execution / provider verification — ادّعاءٌ أنّ المزوّد أعاد صدى طلبنا
```

قيمةٌ من درجة 3 (`Policy / Approval / Identity Authority`) قد تسندُ **سلطةَ استقلال** داخل معيارٍ مشتقّ، دون أن تصبح نيّةً للمستخدم؛ وذاكرةُ الدرجة 9 قد تُغذّي الـresolve دون أن تصبح **سلطةَ معيارٍ أو نيّةٍ**؛ ومطابقةُ المزوّد (درجة 5) تُثبت أننا طلبنا شيئًا، لا أنّه كان هو المطلوب (§10.9 و§10.10 و§11).

## 20. اختبار أي إضافة مستقبلية

قبل أي إضافة نسأل:

- هل تغير هوية KAI؟
- هل تمنح قدرة على Authorization أو Execution أو Completion؟
- هل تستطيع توسيع Contract؟
- هل يمكن إعادة بناء قراراتها من Evidence؟
- هل يمكن Recovery بأمان؟
- هل تتجاوز Gateway أو Policy أو Approval أو Identity أو Task State؟
- هل تجعل Core أكثر موثوقية أم تجعل Representation أغنى فقط؟
- هل هي Core أم Required Implementation أم Extension أم Experiment أم Future؟

إذا لم تكن الإجابة واضحة، لا نضيفها بعد.

## 21. النموذج النهائي لهوية KAI

```text
KAI =
  1. النموذج يقترح؛ والسلطة تقرر.
+
  2. كل تنفيذ ذي أثر خارجي يمر عبر Boundary محكومة واحدة.
+
  3. Task Contract يثبت قبل قبول التنفيذ المعتمد على النموذج.
+
  4. التنفيذ ينتج Durable Evidence ويمكن استعادته عبر Re-derivation.
+
  5. Completion هو إثبات حتمي لـIntent Fulfillment، وليس مجرد Action Response أو Graph Terminal.
```

كل ما عدا ذلك Supporting Structure أو Extension أو Experiment أو Future Capability.

## 22. الاتجاه الحالي

يجب أن ينتقل المشروع من:

```text
Representation Expansion
```

إلى:

```text
Semantic Closure of Intent Fulfillment
```

الـMilestone المعماري التالي ليس IR Feature جديدة، بل:

> **تعريف دقيق وقابل للاختبار لما يعنيه أن KAI حقق Intent المستخدم، خصوصًا عندما يوجد أكثر من مسار تنفيذ صحيح.**

بعد حسم ذلك يمكن محاذاة التنفيذ حول Completion Model واحد.

وحتى ذلك الوقت:

> **يجب أن يبقى KAI-IR طبقة تمثيل صحيحة، بلا سلطة مستقلة.**
