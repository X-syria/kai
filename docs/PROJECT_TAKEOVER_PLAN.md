# KAI — خطة الاستلام والبدء

## الحالة عند الاستلام

المصدر المستلم على فرع `ci/task-ci-07-db-guard` وبـ working tree غير نظيف. توجد تغييرات محلية وترحيلان غير مثبتين وأدوات تشغيل غير متاحة في بيئة الاستلام الحالية. لذلك تُعامل النسخة كـ handover candidate لا كـ release baseline.

## مرحلة 0: التثبيت (يومان)

- حفظ `git status`, `git diff --stat`, branch وcommit في سجل الاستلام.
- منع أي artifact يحتوي `.env` أو مفاتيح.
- تحديد مصدر التغييرات: commit/branch/patch لكل مجموعة.
- حلّ `alembic heads` إلى رأس واحد مع اختبار قاعدة فارغة.
- تجهيز Python 3.14 وDocker/PostgreSQL أو بيئة CI مكافئة.

**معيار الخروج:** commit نظيف، migration head واحد، لا أسرار، وbaseline قابل لإعادة البناء.

## مرحلة 1: الأثر والأثر الخارجي (أسبوع)

- سجل أدلة append-only مع hash chain واحتفاظ مستقل.
- idempotency key للـ Calendar/Gmail وتخزين provider ids قبل قراءة الاستجابة الثانوية.
- جعل approval/effect/evidence حدوداً ذرية أو تعويضية واضحة.

**معيار الخروج:** اختبارات إعادة المحاولة، انقطاع الاستجابة، وفشل المزود لا تنتج أثراً مكرراً ولا دليلاً مفقوداً.

## مرحلة 2: الحوكمة والتشغيل (أسبوعان)

- تصنيف محتوى مستقل عن اسم الأداة.
- تحقق مستقل من provider effect.
- فصل التنفيذ طويل المدة عن HTTP request بعامل/طابور durable.
- fail-closed للإنتاج وrate limit صحيح لكل حساب.

## مرحلة 3: الجاهزية (أسبوعان)

- RLS أو عزل مركزي enforced، key version/AAD، observability runbooks.
- اختبار ضغط محدود، disaster recovery، وإطلاق تجريبي مُدار.

## قرار البدء

يمكن بدء العمل البرمجي الآن في مرحلة 0 فقط. لا يُسمح بتجربة مستخدمين حقيقيين أو ربط OAuth حي قبل إغلاق الأسرار، الشجرة، الترحيلات، والأثر الخارجي.
